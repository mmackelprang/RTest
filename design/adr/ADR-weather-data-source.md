# ADR-022: Weather Data Source for Sleep-Mode Forecast Display

**Date:** 2026-05-23
**Status:** Accepted (this PR)
**Author:** Claude Architect
**Supersedes:** None
**Superseded by:** None

---

## 1. Context

The kiosk sleep screen (`src/Radio.Web/Components/Pages/Sleep.razor`) currently
shows an anti-burn-in drifting LED clock plus optional now-playing metadata.
We want the sleep screen to alternate between:

- the time (existing display), and
- a **3-day weather forecast** for the listener's location.

The Radio Console codebase has **no weather capability today** — grepping
`src/` returns zero references to "weather", "forecast", "OpenWeather", or
"NWS". This ADR introduces the first weather data source. Because the data
flows the full length of the layered architecture (Infrastructure → API →
Web), and because forecast-style data is reusable (a future "Wake to
Weather" alarm, a small forecast widget on the Home page, etc.), this is
worth deciding cleanly once rather than letting the first caller bake in
shortcuts.

### Decisions already made by the product owner (out of scope to relitigate)

1. **Provider:** US National Weather Service (api.weather.gov) — free, no
   API key, no documented rate limit. US-only is acceptable; the listener's
   household is in the US.
2. **Location config:** UI-configurable ZIP code, persisted in the SQLite
   config store via the existing bridge pattern (ADR-002, plus the
   `IOptionsMonitor` + `ConfigStoreChangeNotifier` mechanism added in
   PR #298). Default ZIP: **27312** (Pittsboro, NC).

This ADR decides everything else: data model, lookup flow, caching, code
location, configuration schema, and testing.

## 2. Decision

### 2.1 Data model

Defined in `src/Radio.Core/Models/WeatherForecast.cs`. Two records, both
immutable, both serializable as JSON over the API.

```csharp
namespace Radio.Core.Models;

/// <summary>
/// A 3-day forecast for a single location. The API returns this DTO as the
/// payload of GET /api/weather/forecast.
/// </summary>
/// <param name="Zip">ZIP code the forecast was retrieved for.</param>
/// <param name="LocationName">Human-readable place name (e.g. "Pittsboro, NC").
/// Sourced from the ZIP-to-coordinates lookup; falls back to the raw ZIP
/// if the geocoder doesn't return a place name.</param>
/// <param name="GeneratedAtUtc">Wall-clock time the upstream forecast was
/// generated by NWS (forecastGenerator.generatedAt). Used by the UI to show
/// "as of HH:mm" and by callers to detect stale data.</param>
/// <param name="FetchedAtUtc">Wall-clock time WE fetched/refreshed this
/// forecast. Diverges from GeneratedAtUtc when we serve cached data.</param>
/// <param name="IsStale">True when the cache entry is past its TTL but is
/// being served because the upstream fetch failed (stale-while-revalidate).
/// UI should render a subtle "stale" affordance in this case.</param>
/// <param name="Days">Exactly three entries: today, tomorrow, day-after.</param>
public sealed record WeatherForecast(
    string Zip,
    string LocationName,
    DateTimeOffset GeneratedAtUtc,
    DateTimeOffset FetchedAtUtc,
    bool IsStale,
    IReadOnlyList<WeatherDay> Days);

/// <summary>
/// One day of the forecast. Temperatures are stored in both units so the UI
/// can switch without a round-trip; downstream callers pick the field that
/// matches their <see cref="WeatherForecastOptions.TemperatureUnit"/>.
/// </summary>
public sealed record WeatherDay(
    DateOnly Date,
    string DayName,                       // "Today", "Tomorrow", "Mon"
    int HighF,
    int LowF,
    int HighC,
    int LowC,
    string ConditionShort,                // "Sunny", "PM Showers"
    string ConditionLong,                 // verbose NWS narrative
    int PrecipitationProbabilityPct,      // 0..100
    string IconKey,                       // see icon mapping table below
    string? NwsForecastUrl);              // optional debug link to NWS source
```

Notes:

- `IconKey` is a small, stable identifier (e.g. `"sunny"`, `"partly-cloudy"`,
  `"rain"`) — **not** a Material/MDI icon name and **not** an NWS URL. The
  Web layer maps `IconKey` to a concrete `MaterialIcons` constant. This
  keeps Core free of UI-library dependencies and lets Designer change the
  icon set without an API change.
- The `Days` array is **always exactly three entries** when `IsStale=false`.
  If only fewer days are available from NWS for some reason (e.g. it's late
  evening and only "Tonight"/"Tomorrow"/"Tomorrow Night" remain), we still
  collapse to three calendar days; the service is responsible for
  aggregating day+night periods into a single `WeatherDay`.
- `DateTimeOffset` over `DateTime` everywhere — the kiosk's local time and
  NWS's UTC timestamps need to compare correctly.

### 2.2 NWS lookup flow

NWS requires a three-call chain. We encapsulate the whole chain inside
`NwsWeatherService` so callers see only `Task<WeatherForecast>`.

```
ZIP (e.g. "27312")
  │
  ├─► [1] ZIP → (lat, lon, placeName)
  │     GET https://api.zippopotam.us/us/{zip}
  │     (cached forever per ZIP — ZIP centroids do not move)
  │
  ├─► [2] (lat, lon) → forecast URL + grid
  │     GET https://api.weather.gov/points/{lat},{lon}
  │     Returns: properties.forecast (URL), properties.relativeLocation.properties.city/state
  │     (cached per ZIP for 30 days — grid assignment is stable)
  │
  └─► [3] forecast URL → 7-day forecast periods
        GET <properties.forecast>
        Returns: properties.periods[] with name/temperature/shortForecast/
                 detailedForecast/probabilityOfPrecipitation/icon
        (cached per ZIP for the configured RefreshIntervalMinutes, default 60)
```

#### ZIP-to-coordinates: zippopotam.us vs. static table

**Choice: zippopotam.us, with a small built-in fallback table.**

| | zippopotam.us | Static table |
|---|---|---|
| Coverage | All US ZIPs | Whatever we ship |
| Network dep at startup | Yes (one-time per ZIP, then cached forever) | No |
| Size | Zero | ~40 KB for a couple hundred common ZIPs, ~3 MB for all 41k ZIPs |
| Maintenance | None | Periodic data refresh |
| Failure mode | Offline / DNS failure → fall back | Always works |

Rationale: the kiosk is normally online (it relies on streaming and Cast),
and the ZIP→lat/lon result is cached **persistently in memory for the
lifetime of the process** (and even one round trip per ZIP per process
restart is a non-issue at our usage volume). To handle the edge case where
the box boots without internet, we ship a **tiny fallback table** in the
service containing **the default ZIP (27312)** and any other ZIPs we
explicitly add later. If both zippopotam.us and the fallback table fail
for an unknown ZIP, the service returns a typed failure (see §2.3 failure
mode) and the UI hides the forecast pane.

We do **not** ship the full 41k-ZIP dataset — it bloats the deployable
artifact and is not worth it for a single-household appliance.

### 2.3 Caching strategy

In-memory only, via `IMemoryCache` (already part of the
`Microsoft.AspNetCore.App` shared framework — no new NuGet dep). Three
distinct cache entries per ZIP:

| Cache key | TTL | Notes |
|---|---|---|
| `weather:zip:{zip}:coords` | Process lifetime (no expiry) | ZIP centroid never changes |
| `weather:zip:{zip}:grid` | 30 days | NWS grid assignment is stable |
| `weather:zip:{zip}:forecast` | `RefreshIntervalMinutes` (default 60 min) | Plus a 24h "stale-serve" entry |

#### Stale-while-revalidate behavior

The forecast cache has two side-by-side TTLs:

- **Fresh TTL** (default 60 min): if the cached entry is younger than this,
  return immediately. No upstream call.
- **Stale TTL** (24 hours): if the cached entry is older than Fresh but
  younger than Stale, we attempt a refresh. On refresh success, return the
  new value. On refresh **failure** (HTTP error, timeout, parse error),
  return the cached value with `IsStale=true` and log a Warning. This
  prevents a transient NWS outage from blanking the screen.

If the entry is older than the Stale TTL **or** doesn't exist, we attempt a
fetch and either succeed or surface a typed failure to the caller (see
"Failure modes" below).

Stale refreshes are **lazy** (triggered on the next request) — we do not
need a background refresher hosted service for v1. The kiosk re-fetches
hourly from the sleep screen anyway.

#### No persistence to SQLite

Forecast data is short-lived and re-fetchable. Persisting it to disk would
add migration overhead and offer no real benefit — process restarts are
infrequent enough that re-fetching three URLs at boot is fine.

#### Failure modes

The service exposes:

```csharp
public interface IWeatherService
{
  /// <summary>
  /// Get the 3-day forecast for the configured ZIP, honoring the cache
  /// and stale-while-revalidate rules. Returns null when no forecast can
  /// be served (cache empty + upstream unreachable, or ZIP invalid).
  /// Never throws on upstream failure — the UI should treat null as
  /// "hide the forecast pane".
  /// </summary>
  Task<WeatherForecast?> GetForecastAsync(string zip, CancellationToken ct = default);
}
```

Failure handling matrix (drives the UI):

| Situation | Service returns | UI behavior |
|---|---|---|
| Fresh cache hit | `WeatherForecast` with `IsStale=false` | Render normally |
| Stale cache + refresh succeeds | new `WeatherForecast`, `IsStale=false` | Render normally |
| Stale cache + refresh fails | cached `WeatherForecast`, `IsStale=true` | Render with subtle "as of HH:mm" affordance |
| No cache + upstream fails | `null` | Hide forecast pane entirely; sleep clock continues to show time only |
| Invalid ZIP (zippopotam returns 404) | `null` | Hide forecast pane; surface error to Settings UI separately |

**The sleep screen MUST gracefully tolerate `null`.** That is the
load-bearing contract Designer and Builder need to honor.

                                    # return Core models directly.

#### Why no SignalR push?

The sleep screen refreshes once per hour. A polled HTTP GET on hourly
intervals (with a jitter of ±5 min so all kiosks don't hit NWS at the same
top-of-hour second) is dramatically simpler than introducing a new SignalR
hub. SignalR earns its complexity when data changes faster than ~30 s; this
data changes every ~60 min.

If a future use case needs sub-minute updates (e.g. tornado warnings), we
add a `WeatherHub` then. Not now.

#### Why a Web-layer poll, not a backend hosted service?

A `BackgroundService` that refreshes the cache every hour regardless of UI
presence wastes calls and battery (yes, NWS doesn't rate-limit, but it's
still impolite). Lazy refresh on demand means: kiosk asleep with no
viewers → no calls; kiosk awake → calls when someone is actually looking.

### 2.5 Configuration model

New section `Display:Weather` in the SQLite config store. Bound via
`IOptionsMonitor<WeatherDisplayOptions>` so toggling Enabled in the UI
takes effect on the next forecast request without restart (same pattern as
`FingerprintingOptions` consumers — see "Config Bridge" in MEMORY).

```csharp
namespace Radio.Core.Configuration;

public sealed class WeatherDisplayOptions
{
  public const string SectionName = "Display:Weather";

  /// <summary>Master switch. When false the sleep screen never shows the
  /// forecast pane and the API returns 404 / disabled.</summary>
  public bool Enabled { get; set; } = true;

  /// <summary>ZIP code (5 digits, US only). Default is the user's home ZIP.</summary>
  public string Zip { get; set; } = "27312";

  /// <summary>Forecast cache fresh-TTL in minutes. NWS updates roughly
  /// hourly, so anything less aggressive than 60 minutes is wasted bandwidth.
  /// Valid range: 15..360.</summary>
  public int RefreshIntervalMinutes { get; set; } = 60;

  /// <summary>"F" or "C". Selects which of (HighF/LowF) or (HighC/LowC)
  /// the UI displays. The data model carries both so the toggle is local
  /// to the UI.</summary>
  public string TemperatureUnit { get; set; } = "F";

  /// <summary>Contact email used in the NWS User-Agent header per their
  /// policy. Reuses the same value as Fingerprinting:MusicBrainz:ContactEmail
  /// if set there; falls back to a generic if unset (NWS allows this but
  /// they may rate-limit anonymous traffic).</summary>
  public string ContactEmail { get; set; } = string.Empty;
}
```

Storage shape in the SQLite config store (`Config_sqlite` table, flattened
keys via the bridge from PR #298):

```
Display:Weather:Enabled                = "true"
Display:Weather:Zip                    = "27312"
Display:Weather:RefreshIntervalMinutes = "60"
Display:Weather:TemperatureUnit        = "F"
Display:Weather:ContactEmail           = ""
```

These bind to `WeatherDisplayOptions` via the standard
`services.Configure<WeatherDisplayOptions>(config.GetSection("Display:Weather"))`
call inside `AddRadioWeather()`. The `Display:*` top-level section is new
(today's UI-display-ish config sits under `AudioOutput:DeviceDisplay`,
which is audio-output-scoped). Keeping weather under its own `Display:*`
namespace leaves room for future non-audio display config (e.g.
`Display:Clock:Format`, `Display:Sleep:DriftAmplitude`).

### 2.6 Dependencies

| Need | Source | New NuGet? |
|---|---|---|
| HTTP client | `IHttpClientFactory` (already wired in 3 services) | No |
| JSON deserialization | `System.Text.Json` | No |
| In-memory cache | `Microsoft.Extensions.Caching.Memory` (in shared framework) | No |
| Options binding | `Microsoft.Extensions.Options` (already used) | No |

**Zero new NuGet packages.** This was an explicit design constraint to keep
the dependency footprint of a small feature small.

#### NWS User-Agent requirement

NWS requires a `User-Agent` header containing a contact email. From
[api.weather.gov docs](https://www.weather.gov/documentation/services-web-api):

> A User Agent is required to identify your application. This string can be
> anything, and the more unique to your application the less likely it will
> be affected by a security event. If you include contact information
> (website or email), we can contact you if your string is associated to a
> security event.

We construct it as:

```
RadioConsole/1.0 (+<ContactEmail or fallback>)
```

`WeatherServiceExtensions.AddRadioWeather()` registers a named
`HttpClient("nws")` with the User-Agent baked into `DefaultRequestHeaders`,
rebuilt when `IOptionsMonitor<WeatherDisplayOptions>` fires a change.

### 2.7 API surface

```
GET /api/weather/forecast              → 200 WeatherForecast (uses configured ZIP)
GET /api/weather/forecast?zip=12345    → 200 WeatherForecast (override)
                                       → 404 if Display:Weather:Enabled = false
                                       → 503 if upstream fails AND no cache available
                                       → 400 if ZIP isn't 5 digits
```

The 503 case is what triggers the UI's "hide pane" behavior. We
deliberately do **not** return 200 with a null body — JSON null vs missing
field is a footgun, and the `WeatherForecast?` nullability is a service-
internal concept. At the HTTP boundary, an unavailable forecast is a 503,
and the typed `WeatherApiService` in the Web layer catches that and
returns `null` to the page.

### 2.8 Testing strategy

**Unit tests** (`tests/Radio.Infrastructure.Tests/Weather/`):

- `NwsWeatherServiceTests` — mocked `HttpMessageHandler` returning canned
  `points` and `forecast` JSON fixtures. Assert:
  - Three-day truncation correctness (NWS returns up to 14 periods of day/
    night; we collapse to 3 calendar days)
  - Day+night period aggregation (high comes from day period, low from
    night period of the same date)
  - Icon mapping coverage (every NWS icon prefix → a valid `IconKey`)
  - Cache hits don't call the handler
  - Stale entry + handler failure → returns cached with `IsStale=true`
  - Cache miss + handler failure → returns null
  - `Enabled=false` → service returns null without touching HTTP
- `NwsIconMapperTests` — exhaustive table of NWS icon URLs from
  [NWS icon docs](https://www.weather.gov/forecast-icons) mapped to our
  `IconKey` strings, with a fallback (`"unknown"`) for unrecognized URLs.
- `ZipCoordinatesResolverTests` — fallback-table hit, network-success path
  (mocked), zippopotam 404 → null.

Fixtures live under `tests/Radio.Infrastructure.Tests/Weather/fixtures/`
as JSON files (one per upstream response type), loaded by a tiny
`LoadFixture(name)` helper.

**Integration tests** (`tests/Radio.IntegrationTests/Weather/`):

- One `[Category("Integration")]` test that hits the real NWS API with the
  default ZIP and asserts the chain returns a 3-day forecast with sensible
  values (temps in -40..140°F, probabilities in 0..100, icon keys
  non-empty). Excluded from the default CI workflow per the convention
  noted in CLAUDE.md / MEMORY ("CI workflow excludes E2E tests and
  Category=Integration tests").

No test should run against the live API in regular CI.

### 2.9 Observability

Log at:

- `Information` on each successful upstream fetch with elapsed ms.
- `Warning` on stale-serve (refresh failed, returning cached).
- `Error` on hard failure (no cache, upstream failed) with the exception.
- `Debug` on cache hit.

No new metrics counters in v1. If the feature stabilizes and we want
dashboards, add `weather.fetch.duration`, `weather.fetch.success`,
`weather.cache.hit` to `Radio.Metrics` later.

## 3. Out of Scope (explicitly)

This ADR does **not** cover and intentionally defers:

- **Multi-location support.** The data model carries a `Zip` field per
  forecast precisely so a future multi-location feature is additive, but
  v1 is single-ZIP. A future ADR would add `IReadOnlyList<string> Zips`
  and a UI for managing multiple locations.
- **Hourly forecast detail.** NWS provides an `/forecast/hourly` endpoint;
  we don't need it for a 3-day daily summary. Adding it later is a new
  service method and a new DTO — no change to what this ADR specifies.
- **Severe weather alerts.** NWS `/alerts/active` is an entirely separate
  workflow (push-like, low-latency, lifecycle-managed). Worthy of its own
  ADR if/when the user wants the radio to override audio with a tornado
  warning.
- **Astronomical data (sunrise/sunset/moon phase).** Not in NWS; would
  require a second provider. Out of scope.
- **Non-US locations.** NWS is US-only by charter. International support
  would require a different provider (Open-Meteo is a strong candidate)
  and is a future ADR.
- **Persistent forecast history / analytics.** No reason to persist what's
  trivially re-fetchable. If a "show me what we forecast last week vs.
  what actually happened" feature comes up, it's a new feature and a new
  storage decision.
- **UI design.** Designer owns the visual layout of the forecast pane in
  the sleep screen, including the day/time alternation cadence, layout for
  3 days, icon choice, and stale-data affordance. This ADR pins the data
  contract; it does not pin the rendering.

## 4. Consequences

### Good

- One round of NWS calls per ZIP per hour. Effectively free.
- Sleep screen degrades gracefully on outage (stale → empty pane), never
  crashes, never blocks rendering.
- Zero new NuGet dependencies; everything is in the shared framework.
- The `IWeatherService` interface is small enough that any future provider
  swap (Open-Meteo for international, OpenWeatherMap for richer data) is a
  one-class change in `Radio.Infrastructure/Weather/`.
- The `Display:*` config namespace gives us a clean home for future
  display-related toggles that aren't audio-output-scoped.
- Forecast data shape (with both °F and °C, with separate `IconKey`, with
  `IsStale`) is concrete enough that Designer can lay out the UI from the
  field list alone and Builder can implement against the interface
  without further architecture decisions.

### Bad / costs

- We've introduced our first external HTTP dependency in `Radio.Infrastructure`
  that runs at user-visible cadence (existing externals are MusicBrainz/
  Shazam, called from background fingerprinting only). An NWS outage at
  exactly the moment a user wakes the kiosk could surface a brief
  "forecast unavailable" gap. Mitigated by stale-while-revalidate and
  silent pane-hiding.
- Two-step (actually three-step) lookup chain means a first-fetch for a
  new ZIP makes three HTTP calls back-to-back. Cold-start latency is
  bounded (~500 ms typical, ~3 s on slow networks). Acceptable since
  cold-start happens once per ZIP per process and we cache aggressively.
- ZIP-only location locks us into US; mitigated only by an explicit
  future-ADR commitment.
- `IconKey` adds an indirection (NWS URL → IconKey → MdiIcon constant)
  rather than passing the icon name through directly. This is deliberate
  isolation but it does mean Builder must implement and maintain the
  mapping table in two places (NWS URL prefix → IconKey in Infrastructure,
  IconKey → MdiIcon in Web).

### Neutral

- The 3-day truncation is a product choice (sleep screen real estate);
  changing it to 5 or 7 days is a config knob away if we ever want it.
- `WeatherDisplayOptions.ContactEmail` overlaps semantically with
  `MusicBrainzOptions.ContactEmail`. We could refactor to a shared
  `Display:ContactEmail` or `App:ContactEmail` root key later, but doing
  that now would couple this PR to a refactor of an unrelated subsystem.
  Leave both for now; consolidate when a third consumer appears.

## 5. Alternatives Considered

### 5.1 OpenWeatherMap (with API key)

Pros: international coverage, richer data, sunrise/sunset bundled in.
Cons: requires an API key (which means secrets management, key rotation,
and a free-tier rate limit we'd have to respect). The user explicitly
chose NWS to avoid all of that. Revisit only if/when international support
becomes a requirement.

### 5.2 weather.gov RSS / XML feeds

NWS publishes per-zone RSS feeds that don't require the points→forecast
chain. Cons: deprecated, lower data quality (no `probabilityOfPrecipitation`,
no clean icon mapping), and the JSON API is the documented modern surface.
Not worth optimizing for one fewer HTTP call.

### 5.3 SignalR push instead of HTTP poll

A `WeatherHub` could broadcast a single forecast object to all connected
Web clients. Cons: adds a backend `BackgroundService` to drive refreshes
regardless of viewer presence; introduces a hub for a single, slowly-
changing payload. Reconsider when we have more than one consumer of
weather data or when refresh cadence drops below 30 s.

### 5.4 Backend `BackgroundService` warmer with HTTP poll for delivery

A hosted service refreshes the cache every hour; the API serves out of
the warm cache. Pros: guaranteed-fresh first fetch. Cons: wastes calls
when nobody is viewing; adds a hosted service for negligible benefit.
The lazy stale-while-revalidate strategy gives us 99% of the same UX
without the background work.

### 5.5 Embed the entire 41k-ZIP centroid dataset

Pros: zero network calls for geocoding. Cons: ~3 MB of static data shipped
with every deploy for a single-household appliance that knows its own
ZIP. Not worth it. We ship a 5-entry fallback containing the default ZIP
and call zippopotam.us for the rest, caching forever.

### 5.6 Put weather config under `AudioOutput:DeviceDisplay:*`

The user prompt suggested this namespace as the model. Rejected: weather
has nothing to do with audio output, and `DeviceDisplay` is specifically
the device-list filtering/friendly-naming subsystem (see
`AudioOutputOptions.DeviceDisplay`). A new top-level `Display:Weather`
keeps the concern separated and gives us a `Display:*` namespace for
future non-audio UI config (sleep clock format, drift parameters, etc.).

## 6. Migration / Rollout

This is a net-new feature; nothing to migrate.

- No SQLite schema changes (config bridge uses the existing key/value
  `Config_sqlite` table).
- Default `Display:Weather:Enabled = true`, `Zip = "27312"` means the
  feature lights up on first deploy without any user action.
- Setting `Enabled = false` returns the sleep screen to its current
  clock-only behavior (the UI should treat absent forecast as the existing
  display).

## 7. Open Questions

1. **Built-in fallback table contents** — does the user want just `27312`
   in the fallback table, or should we ship the centroids for a handful of
   common ZIPs (e.g. NYC, LA, Chicago) "just in case"? Recommendation:
   ship only `27312` for v1; add more if/when a second household uses this.
2. **Day-name format** — `"Today"` / `"Tomorrow"` / `"Mon"` per the prompt,
   but should day 3 be `"Mon"` or `"Monday"`? Recommendation: short
   3-letter, matching the prompt's example. Designer can confirm in the
   UX spec.
3. **Contact email source** — fall back to a hardcoded `radioconsole@localhost`
   if the user hasn't set one, or require the user to set it before
   weather works? Recommendation: hardcoded fallback so the feature works
   out-of-the-box. Surface a soft nag in the Settings UI later.

These are UX-flavored questions and should be answered by Designer in the
sleep-mode design spec, not by another ADR.

## 9. Handoffs

- **Designer:** lay out the sleep-mode forecast pane (3-day grid, day-name
  format, icon set, stale affordance, alternation cadence between clock
  and forecast). Data contract is §2.1; failure-mode UI contract is §2.3.
- **Planner:** write the implementation plan against §2.4 (file layout) and
  §2.8 (testing). The full chain is roughly 8 files (1 interface, 1 options
  class, 1 forecast record, 1 service impl, 1 icon mapper, 1 zip resolver,
  1 DI extension, 1 controller) plus tests.
