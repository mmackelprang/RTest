### Active follow-up arc — BT clock-skew "underwater" audio (selected 2026-05-22)

PR #400's observability surfaced 217–391 ppm clock skew between the BT phone clock and the local speaker clock during BT → Cast playback — ~10–20× over BT A2DP spec. The skew is unfixable in software (two crystals cannot be sync'd); the goal is to make the compensation that masks it less audible.

- **Research**: [`docs/research/2026-05-22-bt-clock-skew-measurement.md`](research/2026-05-22-bt-clock-skew-measurement.md) — measurement methodology, architectural analysis, mitigation menu
- **Plan in flight**: [`docs/plans/2026-05-22-bt-drift-compensation-refinement.md`](plans/2026-05-22-bt-drift-compensation-refinement.md) — Path C: smaller, more-frequent compensation events with cosine-ramp crossfade smoothing. Branch `feat/bt-drift-compensation-refinement`.
- **Path D shipped** (PR #404 / commit `781a455`). UAT showed objective metrics REGRESSED across all 3 criteria — but diagnosis revealed this was a measurement artifact from a previously-undiagnosed dual-audio-path issue, not a Path D failure.

### Active follow-up arc — BT dual-routing fix + output picker UI (selected 2026-05-22)

`pactl list sink-inputs` on radio revealed **two independent audio paths** feeding the local soundbar simultaneously:
1. **Path A (designed)**: BT → Radio.API → audio engine → outputs
2. **Path B (rogue)**: BT → PipeWire stream-restore → default sink directly (bypassing Radio.API entirely)

The dual-path explains both Mark's "audio from both soundbar AND Cast" complaint AND the Path D regression (the resampler added latency to Path A while Path B remained delay-free, creating comb-filter "underwater" artifacts).

- **Research**: [`docs/research/2026-05-22-bt-dual-routing-investigation.md`](research/2026-05-22-bt-dual-routing-investigation.md)
- **Plan: WP rule (Part 1, critical-path)**: [`docs/plans/2026-05-22-wp-bt-route-exclusivity.md`](plans/2026-05-22-wp-bt-route-exclusivity.md) — WirePlumber config that prevents BT A2DP from auto-routing to default sink. Without this, Path D can't be measured cleanly. ~30 LOC infra config.

**A second, larger defect was folded in because the owner hit it live while testing the first.** `Deploy-ToLinux.ps1:376` relaunches the kiosk with `DISPLAY=:0` on a **Wayland** box — a defect the script's own comment at `:369-374` names as *"KNOWN DEFECT, deliberately not fixed here."* **Every deploy therefore leaves the screen dead.** The replacement is verified by hand, not proposed: `systemd-run --user --collect google-chrome --kiosk … --ozone-platform=wayland …`, which starts the browser from the graphical session's own service manager and so inherits that session's `WAYLAND_DISPLAY` / `DBUS_SESSION_BUS_ADDRESS`. **Confirmed by 2 established connections to `:5002` afterwards — and that count, not process existence, is the meaningful check: during the 2026-08-02 outage Chrome was running and `radio-web` returned 200 for ~33 hours while the count was 0.**

### Physical input — the four cabinet knobs (selected 2026-08-19, executing)

**The project's first physical-input surface, and the largest untested hardware path in it.** Four rotary encoders with shaft buttons (a Pi Pico running [RotaryUsb](https://github.com/mmackelprang/RotaryUsb), USB HID) mount permanently in the restored console face, engraved **`VOLUME · SOURCE · PRESETS · TUNING`** — an order that is final and, once the escutcheon is drilled, the only irreversible decision in the whole GA punch list.

Design is approved in full: [`HANDOFF-rotary-encoder-mapping.md`](design-handoffs/HANDOFF-rotary-encoder-mapping.md) (Rev 3), consumed by [`HANDOFF-GA-PUNCH-LIST.md` §3.0](HANDOFF-GA-PUNCH-LIST.md). **Designer §12.2 flagged the absence of a roadmap row for physical input; this is that row.**

**Why this arc is priced as three-plus weeks rather than "wire up a HID device".** The shipped decoder spoke an **8-byte sbyte-delta report the device does not send** — the real Input Report is 37 bytes of `int32` positions and free-running movement accumulators — so every UX behaviour in the handoff rested on delta values that were garbage. Two consequences shaped everything downstream. First, **accumulator semantics is forced by the protocol, not merely preferred** (there is a reset-position command and no set-position command), which makes the re-baseline rule a safety requirement: on every connect the first sample per encoder is recorded and discarded, or a lead knocked loose and re-seated delivers every detent turned during the outage **as one delta, on the volume knob**. Second, **the device's factory acceleration is a genuine hazard** — measured live on this hardware at `step=1` with a ×50 tier, which at the host's 2 % per unit is **one detent from silence to full**, in a living room, from a knob a guest may be touching for the first time. Host clamps applied unconditionally are what make the window between connect and a verified configuration push survivable.

**Remaining after these:** `ENC-6` (the three-state wake model) and `ENC-15` (the touch-wake gate) are coupled and now carry a live finding against them — the gate **failed**, and structurally: the touchscreen is powered by the panel and leaves the USB bus when the panel blanks, and the encoder exposes only `/dev/hidraw3` with no evdev node, so neither is an independent hardware wake source. `ENC-8` (the Settings surface), `ENC-12` (the config-fault notification) and `ENC-14` (diagnostics and calibration) complete the arc; `ENC-9` (visualisation's move to the touchscreen) is P1 and **not yet queued**, and `ENC-7` has made it more load-bearing than it looks: removing the visualiser knob removed the **last writer** of `VisualizationModeService`, so `CycleMode`/`ToggleEnabled` have no callers, `ModeChanged` cannot fire, and the `VisualizationModeChanged` broadcast plus `VisualizerPanel`'s subscription to it are unreachable. The capability survives on Home's six-segment picker — which never went through that service — but the cross-circuit sync does not. `ENC-9` is where that chain gets either wired up or deleted; see `design/FUTURE-WORK.md` §17.

**The two rules that shaped the interaction design, and that a later change should not casually reverse.** (1) **The Action model:** a press performs one named, immediate action, and no knob's button ever changes what turning that knob does. The device has no LEDs and no display, so a mode would be a mode you cannot see — and the way a person resolves "which mode is this in?" is to turn it and find out, which on a volume knob costs the room. (2) **Preview-then-commit on both selector knobs:** live-commit-per-detent would tear down and stand up an audio source at every detent, straight into two of this repo's open audio bugs.

## Queued (intent recorded, not yet scoped)

### Voice control — Home Assistant Assist integration (queued 2026-08-09)

**Goal**: hands-free voice control of the console ("play vinyl", "tune to 98.5", "cast to the living room", "what song is this?") with spoken responses routed through the console's own ducking/TTS event pipeline. The touchscreen stays owned by the Blazor UI — voice state (listening/processing/responding) renders as Blazor overlay components we build, not a separate voice UI.

**Origin**: 2026-08-09 evaluation of [voice-satellite-card-integration](https://github.com/jxlarrea/voice-satellite-card-integration) (browser-based HA voice satellite). Verdict: it is a Home Assistant *frontend* engine — it only runs on HA-served pages, cannot embed in a non-HA app, and its browser-resident wake-word inference is a poor fit for radio's memory budget. Its architecture (client-side wake word → HA Assist pipeline → intents → device actions) is the template; the implementation here should use HA + Wyoming protocol services instead. Licensing note: that project is AGPL-3.0 and this repo is Apache-2.0 — reference its ideas, do not lift its code.

**Host constraints (verified against `homelab` 2026-08-09)**:
- **radio** (`.50`, N100, 3.6 GiB RAM) is memory-starved — 2.9 GiB used + 2.4 GiB swap at last capture; homelab's standing rule is "don't add anything resident casually." No Docker. The gdm desktop session is load-bearing (PipeWire capture + the GV Chrome session). Anything added on radio must be tiny (≈50 MB resident, no browser, no HA).
- **No Home Assistant deployment exists anywhere in the homelab** (remote-access spec 2026-07-24 states this explicitly) — standing one up is part of this work, not a prerequisite someone else owns.
- **appserver** is the natural HA/STT host: the Docker host, with a GTX 1660 SUPER (6 GiB VRAM, currently serving Ollama) for GPU speech-to-text. Runner container limits alone (16+16+24 GB) imply substantial RAM, but exact free RAM/VRAM is not captured in homelab — verify `free -h` / `nvidia-smi` before install, and account for Ollama VRAM contention.

**Conflict analysis vs the GV Chrome / rotary-phone stack (verified against homelab 2026-08-09)** — the design below is shaped to *not touch* the load-bearing pieces documented in `radio/services/rotary-phone.md` and `radio-base.md`:
- **No browser anywhere in this design.** The GV trunk depends on the logged-in desktop Chrome (CDP `:9224`, cookie refresh cron every 20 min, `mute-gv-browser.py` driving its audio). Voice capture runs as a backend process, so nothing competes with or restarts that Chrome — this is also the decisive reason the browser-based Voice Satellite engine / HA-iframe alternative stays rejected.
- **Microphone isolation**: voice uses a **dedicated USB mic, addressed by its PipeWire node name — never `default`**. PipeWire tolerates shared capture, but pinning the node means that even if GV Chrome ever opens a mic, the two never contend for the same device, and `radio-bt-setup.service`'s PipeWire defaults are left alone.
- **Session plumbing**: capture rides the same `mmack` seat0 PipeWire socket radio-api already uses for BT capture (`/run/user/1000/pipewire-0`, `Linger=no`, `radio-pipewire-access` ACL) — a known, already-mitigated pattern, not a new one. A headless rebuild breaks voice capture the same way it breaks BT capture; same DR note covers both.
- **Ports**: rotary-phone owns SIP `udp/5060`/`5061`, GV-bridge RTP `5070`, RTP `49000+`, SCO `49100+`, CDP `:9224`; payload HTTP is `5000`/`5002`/`5004`. The satellite's default Wyoming port (`tcp/10700`, Option A only) collides with none of these; Option B adds no listener at all.
- **Memory/CPU**: wake word and STT run on appserver, never on radio. Radio's added load is PCM capture + streaming (~32 kB/s at 16 kHz mono) — no inference. Option B adds zero resident processes; Option A adds one (~30–60 MB).

**Proposed architecture (to be validated by a research arc before planning)** — two variants for the radio side; both keep wake word + STT + TTS + intent handling on appserver and the UX purely in Blazor:
1. **appserver — new containers**: Home Assistant + Wyoming services: faster-whisper (STT, GPU), piper (TTS), openWakeWord (wake word). Wired together as an HA Assist pipeline.
2. **radio — mic capture, two options**:
   - **Option A — off-the-shelf satellite**: a `wyoming-satellite` systemd unit streams the mic to HA; wake detection stays on appserver (`--wake-uri` pointed at the openWakeWord container). Fastest path to a working pipeline; one new resident process; Blazor state arrives via HA's websocket or a radio-api relay.
   - **Option B — native (preferred end-state): radio-api *is* the satellite.** Radio.Infrastructure already captures PipeWire audio for the BT source; add a mic capture service that streams to HA's **Assist Pipeline WebSocket API** (`assist_pipeline/run`, binary audio frames, pipeline started at the wake stage so detection happens server-side). Pipeline stage events (wake → stt → intent → tts) fan out through the existing SignalR hubs to the Blazor overlay. **Zero new processes on radio, no new listener, voice becomes a first-class Radio Console feature** with its config in the normal appsettings/secrets stores. Cost: more dev work than A; the research arc should validate continuous-stream-over-WiFi behavior (or gate the stream on local VAD) before committing.
   - Sensible sequence: stand the pipeline up with A to validate end-to-end latency/accuracy, then fold capture into radio-api as B and retire the extra unit.
3. **Intent → action**: HA custom sentences → `rest_command` → radio-api REST endpoints (sources, tuning, volume, Cast targets, fingerprinting/play-history for "what's playing").
4. **Blazor overlay**: Radio.Web renders listening/processing/responding state — under Option B this is just another SignalR event stream from radio-api, keeping the UI's dependency surface unchanged (no direct Blazor→HA coupling).
5. **Responses through the cabinet**: HA automations POST to radio-api's TTS/audio-event endpoints so the existing priority-ducking speaks the reply and fades the music back — no satellite speaker path exists in either option.

## Workflow notes
