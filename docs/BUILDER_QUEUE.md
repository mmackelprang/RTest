## Dependency / ordering notes

- **GV-1 is the foundation.** GV-2 and GV-3 both depend on GV-1 (DTOs, the extended `GvBridgeApiService`, the new `PhoneHubService` events, `GvBridgeStatusService`, `PhoneUnreadState`, and the `PhoneMessagesPanel` shell). Builder must merge GV-1 before claiming either.
- **GV-2 and GV-3 are independent of each other** and may ship in either order after GV-1. **Recommended order: GV-1 → GV-2 → GV-3.** One shared coupling: GV-2 introduces the `FeedItem` interleave projection (PR2 Task 5) that GV-3 reuses; if GV-3 is built first, its plan instructs the implementer to introduce that projection there instead.
- **Read experience ships fully today; send lights up later.** Everything in GV-1/GV-2/GV-3/GV-4 except SMS **send** is functional now. **`POST /api/gvbridge/sms/send` has SHIPPED on RotaryPhone** (dark behind their `GVBridge:EnableSmsSend=false`), so the endpoint is not the blocker. **Send is now scoped as GV-5** (ADR-028), which depends only on **GV-3** — not on GV-4, and not on anything external. GV-5 makes send *correct*; flipping `RotaryPhone:Gv:SendEnabled=true` stays a separate two-side decision afterwards (theirs first, then ours).
- **GV-5 is claimable now and is independent of GV-4.** It touches `GvBridgeSendService`, `PhoneTextsPanel`, `MessageBubble`, `PhoneHubService`, and `PhonePage`. The only overlap with GV-4 is `PhoneHubService` (a sibling `.On<>` registration) and `PhonePage` (a sibling handler beside `OnGvSmsReceived`); GV-4 is merged, so there is no conflict — but a Builder rebasing an old branch should expect both files to have moved.

- **SMS send contract reconciliation** — ✅ **SCOPED AND QUEUED as GV-5** ([ADR-028](../design/decisions/2026-07-30-gv-sms-send-contract.md)). The earlier note here framed this as a response-shape mismatch; investigating the as-built endpoint found it is **larger on three axes**:
  - **The request is wrong and fails 100% of sends.** Ours is `SendSmsRequest(string ThreadId, string Text)`; theirs is `SendSmsRequest(string ToNumber, string Text, string? ThreadId, string? ClientCorrelationId = null)`. We POST `{"threadId":…,"text":…}`; `ToNumber` binds **`null`**, their `PhoneNumberNormalizer.TryNormalize(null)` returns false, and the route returns **`400 invalid_number`** — in both reply and new-recipient mode. Send was never functional, only silent.
  - **The taxonomy is nine codes, not eight.** `invalid_text` (400) was missing from the list previously recorded here. Full set: `queued` (200) | `send_disabled` (409) | `rate_limited` (429) | `invalid_text` (400) | `invalid_number` (400) | `auth_unavailable` (502) | `upstream_error` (502) | `timeout` (504) | `error` (500).
  - **We never subscribe to the outbound echo channel.** Outbound messages are broadcast on **`SmsSent`**, never on `SmsReceived`. `PhoneHubService` does not handle it, so GV-3's optimistic→confirmed de-dupe in `PhonePage.OnGvSmsReceived` is **unreachable dead code** and the optimistic bubble would linger un-reconciled. RotaryPhone's poller also re-surfaces the message later with a **different `Id`** by construction, so exact-id matching cannot be the only tier — their own source calls the fuzzy `(text + counterparty + ≤120s)` match "REQUIRED, not optional."
  - **Their `EnableSmsSend=false` is not a blocker.** A dark server returns `409 send_disabled` with no GV call; GV-5 treats that as an **availability state, not a failed send** (no red bubble, no Retry — nothing was sent). Flipping `RotaryPhone:Gv:SendEnabled` remains a separate, later two-side decision; GV-5 ships with it `false`.
- **Audible new-text chime** — belongs in the Radio.API audio layer (ducking-aware), not Blazor (handoff).
