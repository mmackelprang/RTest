Deep design analysis · v1

The console is beautiful. The product underneath it is leaking.

The 1920×720 broadcast-console aesthetic is genuinely strong — DSEG amber LEDs over a calm dark surface, a confident cyan accent, generous touch targets, and per-source color coding all do real work. But the surface is sitting on top of an interface that is still showing the user its raw machinery: FilePlayer-da7eb94888fa43aab0021… as a "source name", 00:03:00.6628571 as a track duration, 850.4% as a memory reading, escaped JSON in a filter input, and a debug-only distortion marker living in production chrome. The work below is mostly about finishing the surface so the design language can do its job.

01

What we're looking at

Setting the frame

Radio.Web is a Blazor Server kiosk app that runs on a fixed 1920×720 touchscreen — likely a Raspberry Pi driving a wide-format panel. It controls a multi-source audio engine (FM/AM radio over RTL-SDR, Bluetooth, USB, vinyl, local files, Google Cast) and surfaces a single home view with three columns: Now Playing, Queue / History, and Visualizer. Secondary pages — Devices, Metrics, History, System, Phone, File Browser — share an 80px top bar that doubles as the global source/output router.

The aesthetic brief is "professional broadcast console / recording-studio rack mount" — DSEG segmented-LCD type in amber for time and frequency, a single electric-cyan accent for active state, and a calm dark palette (#0D0D0F base, #141416 raised). The design system is well-articulated in design-system.css: tokens for surfaces, accents, source colors, touch sizes, animation timing.

The mismatch: the design system promises a calm, opinionated instrument panel. The screenshots deliver something closer to a half-finished admin tool with a beautiful skin on top — raw API IDs, debug controls, broken units, and pages that have one component and acres of empty void below.

02

Don't break these

Real strengths · keep them
✓

Token-first design system

One CSS file owns surfaces, accents, type, motion, and touch sizes. Already the right plumbing — most of the work below is enforcement, not invention.

✓

Per-source color coding

Vinyl violet, radio amber, Bluetooth blue, USB green, file cyan — a smart, learnable mapping that pays off across the whole app once enforced.

✓

DSEG LED type as a signature

Amber segmented display for time, frequency and ghost-segment backgrounds is the single most distinctive visual move in the app. Don't dilute it by using it on regular UI.

✓

Real touch sizing

48/56/64px tokens are defined and route toggles hit them. Better than 90% of admin-style Blazor apps in the wild.

✓

SignalR-driven live state

Now playing, queue count, sleep, source — all push-updated. The user never has to refresh. Lean into this with more live state where it currently isn't.

✓

Three-column home

Now Playing · Queue · Visualizer reading left-to-right is the right shape for a kiosk. Most of the design work for the home page is already done.

What's leaking through

P0 Information architecture MainLayout

The top bar is three different toolbars stacked into one row

Eighty pixels of vertical space are doing four jobs at once: telling time, routing input, routing output, exposing nine global nav targets — plus a temporary debug button. Every cluster uses the same circular-pill shape, so a user can't tell from form alone whether a pill switches a route or navigates a page. The route toggles also conflate two actions (switch source / open detail) by tap counting.

Recommendation
  • Split the bar into three visually distinct zones: a status zone (clock + currently-playing pill), a routing zone (clearly labeled IN → OUT with a connector glyph between them), and a nav zone (rectangular icon+label buttons, not circles).
  • Make active source and active output visible as typeset names, not just colored pills — operators shouldn't have to remember the color code.
  • Move the debug distortion marker behind a dev-tools toggle. It doesn't belong in production chrome.
  • Replace tap-count-to-disambiguate with an explicit affordance: long-press, or a chevron that opens detail.

P0 Data hygiene All pages

API IDs are leaking into the UI as labels

The Audio Source dropdown in older screenshots shows FilePlayer-da7eb94888fa43aab0021… — a UUID-suffixed internal ID being rendered as a human label. Devices show 1 - LG TV SSCR2 (AMD High Definition Audio Device) straight from WASAPI. Tracks fall back to Track 8, Track 9… when metadata is missing. These are all the same problem: the app is showing internal identifiers because the display-name layer is missing or thin.

Recommendation
  • One DisplayName projection on every domain DTO, computed server-side. Never bind a raw Id, RawName, or filename to a user-facing string.
  • Filename fallback: parse leading track-number / disc-number, strip extension, title-case. 08 - We're Ready.flac → We're Ready with subtitle Track 8.
  • Device names: ship a curated alias map for common adapters (VB-Audio, Realtek, HDMI…), with the existing FriendlyNameOverride as the user-edit layer. Show the alias by default, the raw name on long-press.
  • Sources: drop the GUID suffix entirely from the client model. The UI never needs instance identity.

P0 Formatting Queue · NowPlaying

Durations are raw TimeSpan.ToString()

The queue is showing track lengths as 00:03:00.6628571 — hours:minutes:seconds.ticks. No one reads tracks in tick precision. It also makes every column header wider than it needs to be, eating horizontal space the table can't afford. Same problem on History (sub-second precision on date/time).

Recommendation
  • One FormatDuration(TimeSpan) helper used everywhere: 3:00 under an hour, 1:02:14 over an hour, em-dash for unknown.
  • Right-align all duration columns in a tabular-figures monospaced style — already in your --font-mono token.
  • History date format: Today 08:40, Yesterday 14:22, Feb 6 · 11:05 — relative within 48 hours, absolute beyond.

P0 Units · trust Metrics

"Memory Usage Mb: 850.4%" — units are detached from values

The metrics dashboard is rendering every value into the same template ({value}{suffix}) without knowing what unit the metric is in. So Memory Usage Mb ends up labelled 850.4%, signal strength is unitless, latency reads as a bare number, and the underscored category names (TTS, RADIO) look like backend leakage. The dashboard is actively eroding trust in its own numbers.

The page is also a wall of identical tiles — 16+ scalars rendered with zero hierarchy and zero time context. A metrics dashboard with no trend is a list with extra steps.

Recommendation
  • Metric registry has the unit baked in (%, MB, ms, count, req/min). Tile reads it; never assumes %.
  • Group tiles by category with real sub-headers (System / Audio / Radio / Library / TTS) instead of a tiny grey prefix per tile.
  • Inline sparkline for any time-series metric over the selected window — a single <svg> per tile is enough to turn "wall of numbers" into a status board.
  • Color the value only when it's actionable: green for healthy, amber when approaching a threshold, red when over. Don't paint every value cyan.

P0 Bug File Browser

The Filter field is showing escaped JSON

The screenshot of the File Browser shows a Filter dropdown whose value reads "\u0022\u0022\\\u0022\\\\\\\\\u0022\\\\\\\\… — a JSON string that was serialized one too many times and is now being rendered as text inside the input. This is the kind of bug that quietly tells a user the system isn't trustworthy.

Recommendation
  • Find the binding path — likely a filter that's JsonSerializer.Serialize'd for persistence and then bound directly back to a RadzenDropDown value. It should deserialize before bind.
  • Treat the filter as chips, not a text input. Each token is one extension (.mp3, .flac, .wav) with an × — no escaping ever needs to happen.
  • The breadcrumb under the input (Home / D:\) is also wired oddly — it shows D:\ while the drive selector says C:\. Single source of truth for "current path".

P1 Density Radio · Devices · Queue · Visualizer

Most secondary pages use 30% of the screen and waste the rest

The radio page renders a small spinner in the middle of an otherwise blank 640px-tall canvas. Devices shows six rows and stops. Queue lists 3 items and leaves ~480px of empty dark. The kiosk has a fixed viewport — there is no fold to scroll to. Empty space below content reads as "broken" or "still loading", not "minimalist".

Recommendation
  • Treat each page as a fixed dashboard, not a scrolling list. Allocate every region of the 640px content area to a real purpose.
  • Queue: pair the list with a right-side panel — total runtime, upcoming next 3 with art, "save as playlist" CTA. Already have the data.
  • Devices: split into two columns (Outputs | Cast destinations), and add a bottom strip with the actively-routed device state.
  • Radio: while the panel loads, show a skeleton that matches its actual shape (frequency well + band buttons + meter), not a centered spinner.
  • Visualizer: the chart should fill its panel, not sit in a 60%-width box with empty bands. Also make VU / WAVE / SPECTRUM a segmented control, not three tiny outline buttons hugging the corner.

P1 Persistence All non-home pages

You lose Now Playing the moment you leave Home

The Now Playing panel is mounted only at /. As soon as you tap into Devices, Metrics, History, System, or Phone, the user has no visible playback state — no track, no transport, no progress, no source. They can see the queue count on the nav icon and that's it. On a kiosk with no back-pocket phone next to it, that's a real loss.

Recommendation
  • Add a persistent mini-dock at the bottom edge of every non-home page: 56px tall, art thumbnail · title/artist · transport · progress · source dot. Tapping the title takes you home.
  • SignalR is already pushing this state — no new wiring, just a shared component in MainLayout that hides on / (where Now Playing already owns the column).
  • The dock also gives sleep/wake a visible anchor — pulse it dim during sleep instead of blacking the whole screen.

P1 Interaction MainLayout · HandleSourceToggleAsync

The source toggle does two different things depending on tap count

Reading HandleSourceToggleAsync: a first tap on a non-active source switches to it. A tap on the already-active radio source toggles the Radio Control panel on the home page. A tap on the active vinyl/bluetooth source navigates to its dedicated page. The user can't predict from looking at the button which of those three things they're about to get.

Recommendation
  • Source pill = one action: switch to that source. Period.
  • "Open detail view" is a separate affordance — a chevron on the active pill, or a dedicated "Source detail" tile in the home layout that's always visible when the active source has one (Radio, Bluetooth).
  • The Radio Control panel currently replaces the Queue/History panel on home. That's a non-obvious state change. Reserve a small persistent strip in the center column for source-specific controls, and keep Queue/History below.

P1 Hierarchy VisualizerPanel

The visualizer panel buries its own modes and shows raw debug

On the home page right column, the visualizer canvas takes ~70% of its panel, three mode buttons (VU / WAVE / SPECTRUM) live in a top-right corner as small outlined chips, a green Connected pill sits next to them, and the canvas itself has "Updates: 22/sec" burned in as yellow Comic-Sans-y caption text at the bottom-left. That's debug telemetry sitting on a primary visualization.

Recommendation
  • Mode picker should be a segmented control across the top of the panel, full-width — it's the primary control of this view.
  • "Connected" status belongs as a small dot on the panel header, not a labeled pill. And only show red when it's not connected; green-when-fine is noise.
  • "Updates: 22/sec" is dev info — gate it behind the same dev-tools toggle as the distortion marker.
  • Make the visualization itself fill the panel. Add per-mode chrome (frequency labels, dB scale) only where it materially helps reading the signal.
P1 Discoverability design-system.css §19

Hidden scrollbars + no overflow cue = invisible content

* { scrollbar-width: none; } *::-webkit-scrollbar { display: none; } hides every scrollbar globally. The justification in the comment is "kiosk touch UI" — fine, but the screenshots show several pages (Queue with 45 tracks, Devices, System tabs) where there's clearly more content below the fold and nothing tells the user that. The History page also crops a tall content block at ~520px with no gradient or chevron.

Recommendation
  • Keep the bar hidden, but add a thin always-visible thumb (~3px wide, 30% opacity) on scrollable panels so the user knows there's more.
  • Or: a fading mask at the bottom edge of any panel whose content is taller than its box. The CSS is one declaration: mask-image: linear-gradient(to bottom, #000 calc(100% - 24px), transparent).
  • For touch lists, add a momentum-style "✨ scroll for more · N items below" sentinel that fades in when more is hidden.
P2 States Cross-cutting

Loading and empty states are mostly centered spinners

Radio panel: centered RadzenProgressBarCircular in a 640×688 void. Queue panel before data: blank. Devices when there are no Cast devices: nothing. The design-system already defines .skeleton-text, .skeleton-card, .empty-state, and a shimmer animation — they just aren't used.

Recommendation
  • Replace every spinner with a shape-matched skeleton: Now Playing shows blurred art placeholder + 2 text bars + transport row; Radio shows freq-well + band buttons + meter; Queue shows 6 ghosted rows.
  • Build a small <EmptyState Icon Title Action /> Razor component and use it everywhere — current empty handling is ad-hoc.
  • For network/API failures, surface a single inline banner (not a Radzen toast that pops outside the kiosk surface) with a retry button at touch size.
P2 Production hygiene MainLayout.razor:51

The "distortion marker" debug button is in the production top bar

The comment in MainLayout.razor literally says "Debug: Distortion Marker (temporary — remove when done diagnosing)". It's still there. It will be there in six months. It pops a 1-second color flash on every press — a touch-friendly target for accidental input.

Recommendation
  • Move it behind a build-flag gate (#if DEBUG) or a config.diagnostics.enabled setting that defaults false.
  • Better: a hidden tap-and-hold-corner gesture opens a dev panel with this and any other diagnostic actions (audio frame dump, log download). The corner is invisible to normal users and free in screen real estate.
P2 Legibility Type system

Secondary text leans too dim for a 2-foot kiosk viewing distance

--text-medium: #9CA3AF on --surface-base: #0D0D0F hits ~6.8:1 — fine on paper, fine on a desk monitor. On a glossy 12.5" touchscreen at 2-3 feet, combined with smaller body text (13–14px in side panels), several places in the screenshots read as "noise" rather than information. The History "Statistics" sub-labels and the metric category prefixes are good examples.

Recommendation
  • Bump --text-medium to ~#B5BCC9 (~9:1) for body, and reserve the current value for tertiary metadata only.
  • Minimum size for any persistent UI string is 14px. Headers and metric values that people glance at across the room should be 18–20px+.
  • Touch-screen calibration matters: ship the theme in two flavors — desk (current) and kiosk (heavier base weight, ~10% larger type scale, slightly elevated contrast) — and pick at startup based on a config flag.
P2 Semantics Devices · Audio Engine

Status badges all look like "Available" — including the broken ones

On the System Stats page: Audio Engine State: Active - FilePlayer (Stopped) — both "Active" and "Stopped" in the same string with no visual indicator of whether this is good or bad. On Devices, every row says Available in the same blue pill that Default uses. Cast disconnect/connect uses transient toasts that don't persist.

Recommendation
  • Reserve color for state, pills for active / default markers, and plain text for "Available" (it's the steady state, not a status).
  • Parse the Audio Engine string into a structured tuple: { active, current source, current state }. Render with three distinct affordances.
  • Persist Cast connect/disconnect to a small event ribbon below the dock — last 3 events, auto-clear after 30s. Toasts that don't stick are forgotten information.

05

System-level recommendations

Cuts across pages

A. One formatting layer

Create Radio.Web/Formatting/ with FormatDuration, FormatTimestamp, FormatFrequency, FormatBytes, FormatPercent, FormatDeviceName, FormatSourceName. Forbid passing raw DTOs into Razor templates. This single discipline removes ~half the P0 findings above.

B. Skeleton + empty kit

Three Razor components: <Skeleton Shape="now-playing | radio | list" />, <EmptyState Icon Title Body Action />, <ErrorState Title Detail Retry />. Every async-bound surface uses one of these in its @if(_loading) branch.

C. Persistent now-playing dock

Mount once in MainLayout, hide on /. Reads from the same AudioStateHubService already feeding the home page. ~80 lines of Razor + a slot in the layout grid.

D. Dev-tools gate

Triple-tap the top-right corner of the clock to unlock a dev tray containing the distortion marker, fingerprint event log, updates/sec, frame dump, log download. Locks again after 30s of no interaction.

E. Motion budget

You have 30+ @keyframes defined. The screenshots don't show any of them in play. Pick six (page-transition, list-add, list-remove, ken-burns, eq-bounce, track-change) and enforce them on the surfaces that need them. Delete or hide the rest until they're used — they're vocabulary debt right now.

F. Sleep is a screen, not a JS hack

The current sleep flow blacks the screen via JS + a Blazor call. Treat sleep as a first-class route (/sleep) with an ambient view — large clock, faint album art, a single "tap anywhere" hint. Wake on any interaction. Makes the device feel less like "off" and more like "resting".

G. Accessibility passes you'll want anyway

Add aria-label on every icon-only button (90% of the top bar). Make focus rings visible — currently -webkit-tap-highlight-color: transparent across the board removes both touch and keyboard feedback. Use Radzen's Tooltip on the icon nav so the labels appear on long-press.

H. Tighter "source / output" model in UI

Currently three things hold related state: SourcesApiService, DevicesApiService, AudioStateHubService. The UI binds to each separately and races on first load (you'll see brief mismatches in the screenshots — topbar shows FilePlayer source while Now Playing card says Radio). One Razor-side RoutingViewModel that derives from the hub and exposes { source, output, route, isReady } would remove a class of glitches.
