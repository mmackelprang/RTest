# `UI-10` — the Blazor circuit times out every ~30 seconds

[← Builder Queue index](../BUILDER_QUEUE.md)

🟠 **P1.** Filed 2026-09-08, found by the RotaryPhone session while reading our logs during their
outage. **This is ours entirely — they did not touch `radio-api` or `radio-web` at any point.**

## The evidence

`radio-web` logged, repeatedly and roughly every 30 seconds:

```
System.TimeoutException: Server timeout (30000.00ms) elapsed without receiving a message from the server
```

plus a `JSDisconnectedException` at **15:27:06**. ⭐ **It continued after the upstream GV fix at
15:31**, so it is not a symptom of that outage — it is a standing condition that merely became visible
during one.

30000 ms is the SignalR client's default `ServerTimeout`, so this is the **Blazor Server circuit's own
connection**, not a GV call and not one of our visualization hub clients.

## Why it may matter more than it looks

**A dead circuit cannot re-render or refetch, even if the code wants to.** `GV-12` records that the
phone surface never recovered after an 83-minute outage; part of that may be *this* rather than a
missing retry. ⚠ **Establish which before building either** — a retry added on top of a dying circuit
will look like it does not work, and the wrong row gets blamed.

## Scope questions for the plan

1. **Is it the kiosk, the network, or the server?** The kiosk holds a long-lived circuit on the same
   box; a laptop on WiFi is a different case. Check whether the timeouts correlate with one client.
2. **Is `KeepAliveInterval` sane relative to `ServerTimeout`?** The documented rule is
   `ServerTimeout ≥ 2 × KeepAliveInterval`. Check what is configured — the commonest cause, and cheap
   to rule out.
3. **Does the circuit actually recover?** Blazor reconnects by default with a bounded retry, then shows
   the reconnect overlay. Is that overlay ever appearing on the panel? The owner would notice it — so
   if it is *not* appearing, the circuit may be dying and silently re-establishing.
4. ⚠ **Does it correlate with `AUD-18`?** That row records the fingerprint tap returning zero bytes for
   11½ hours on this box, and `CLAUDE.md` records that log volume correlates with audible distortion on
   this hardware. Both could be symptoms of resource pressure. **Check, do not assume** — two rows
   blaming each other is worse than two independent rows.

## Verification

The measurable signal is the one that found it:


## ⛔ CORRECTED 2026-09-09 by `GV-12`'s planning — this row is pointed at the WRONG CONNECTION

**It is not the Blazor circuit.** Established from source, not inference:

- **`App.razor:76` configures the circuit's client with `builder.withServerTimeout(120000)` — 120 s.**
  ⚠ **A circuit on that config cannot emit a `30000.00ms` message.**
- This row's reasoning — *"30000 ms is the SignalR client default, so this is the Blazor Server
  circuit"* — is **right about the default and backwards about the conclusion.** The circuit is the one
  connection here that is **not** on the default.

**The real emitters:** `radio-web` holds exactly four `SignalR.Client.HubConnection`s —
`AudioStateHubService.cs:155`, `AudioVisualizationHubService.cs:83`, `GvTrunkHubService.cs:54`,
`PhoneHubService.cs:69`. **None of them sets `ServerTimeout`**, so all four run the 30 s default.

### ⭐ And the likely root cause is already identified — this row's own scope question #2, answered

**`Radio.API/Program.cs:87` sets `KeepAliveInterval = 30 s`.** Against a 30 s client timeout that
**violates the documented `ServerTimeout ≥ 2 × KeepAliveInterval` rule exactly** — the server may wait
a full 30 s before pinging, by which point the client has already given up.

So the row stands, is **still "ours entirely"**, and is **cheaper than filed** — but every anchor and
the whole diagnosis move from `App.razor`'s circuit to those four hub clients and the API's keep-alive.

### ⛔ Consequence for `GV-12`: it is NOT upstream, and `GV-12` has no dependency on it

`GV-12`'s brief (mine) told its planner that a dead circuit cannot refetch and that this row was
probably upstream. **Both were wrong**, and for a reason neither row had noticed:

⭐ **A reconnected Blazor circuit does not re-mount.** It resumes the **same component instances with
the same fields**; `OnInitializedAsync` runs **once per circuit, not per connection** —
`Program.cs:66-69` says so in its own comment while setting `DisconnectedCircuitRetentionPeriod` to
10 minutes *specifically so state survives reconnects.*

⚠ **So RotaryPhone's framing — "a circuit that drops and re-establishes cleanly produces a re-mount and
therefore a fetch; one that hangs half-dead produces neither" — is false for Blazor Server. Neither
branch produces a fetch.** It sounded like a sharp diagnostic and was relayed twice, by them and then
by me, without either side checking it against the hosting model.

That also explains the 16:07 deploy evidence **better, and without any circuit-health theory**: the
restart forced full page loads, which made **new circuits**, which mounted, which produced their six
requests.

**Net:** this row is a real defect on its own merits, `GV-12` can proceed independently, and neither
blocks the other.
