# `UI-10` — the Blazor circuit times out every ~30 seconds

[← Builder Queue index](../BUILDER_QUEUE.md)

🟠 **P1.** Filed 2026-09-08, found by the RotaryPhone session while reading our logs during their
outage. **This is ours entirely — they did not touch `radio-api` or `radio-web` at any point.**

## The evidence

`radio-web` logged, repeatedly and roughly every 30 seconds:

```
System.TimeoutException: Server timeout (30000.00ms) elapsed without receiving a message from the server
```

plus a `JSDisconnectedException` at **15:27:06**. ⭐ **It continued after the upstream GV fix at
15:31**, so it is not a symptom of that outage — it is a standing condition that merely became visible
during one.

30000 ms is the SignalR client's default `ServerTimeout`, so this is the **Blazor Server circuit's own
connection**, not a GV call and not one of our visualization hub clients.

## Why it may matter more than it looks

**A dead circuit cannot re-render or refetch, even if the code wants to.** `GV-12` records that the
phone surface never recovered after an 83-minute outage; part of that may be *this* rather than a
missing retry. ⚠ **Establish which before building either** — a retry added on top of a dying circuit
will look like it does not work, and the wrong row gets blamed.

## Scope questions for the plan

1. **Is it the kiosk, the network, or the server?** The kiosk holds a long-lived circuit on the same
   box; a laptop on WiFi is a different case. Check whether the timeouts correlate with one client.
2. **Is `KeepAliveInterval` sane relative to `ServerTimeout`?** The documented rule is
   `ServerTimeout ≥ 2 × KeepAliveInterval`. Check what is configured — the commonest cause, and cheap
   to rule out.
3. **Does the circuit actually recover?** Blazor reconnects by default with a bounded retry, then shows
   the reconnect overlay. Is that overlay ever appearing on the panel? The owner would notice it — so
   if it is *not* appearing, the circuit may be dying and silently re-establishing.
4. ⚠ **Does it correlate with `AUD-18`?** That row records the fingerprint tap returning zero bytes for
   11½ hours on this box, and `CLAUDE.md` records that log volume correlates with audible distortion on
   this hardware. Both could be symptoms of resource pressure. **Check, do not assume** — two rows
   blaming each other is worse than two independent rows.

## Verification

⚠ **The honest difficulty: this is a wall-clock symptom on a live box and a unit test cannot show it.**
The measurable signal is the one that found it:

```bash
grep -c 'Server timeout' /opt/radio-console/logs/radio-*.txt
```

**State a per-day baseline before changing anything**, so "it improved" is a comparison rather than an
impression.

⚠ **Do not claim a fix on a quiet hour.** This box has already produced one 11½-hour failure that
looked like nothing for four days.
