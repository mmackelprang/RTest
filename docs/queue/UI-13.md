# `UI-13` — a failed broadcast still advances the change-detection cache, so the delta is never re-sent

[← Builder Queue index](../BUILDER_QUEUE.md)

🟡 **P2.** Filed 2026-09-09 by the `UI-12` Planner, found while enumerating senders and flagged as out
of that row's scope rather than folded in.

## The defect

`Radio.API/Services/AudioStateUpdateService.cs:477` assigns `_lastRadioState` **before** the
`await SendAsync` that broadcasts it:

```csharp
_lastRadioState = dto;          // :477 — cache advanced
await SendAsync(...);           // may throw, may be cancelled
```

The cache is what change-detection compares against. So **if the send throws or is cancelled, the
cache has already moved on, and that delta is never re-broadcast** — the next comparison sees "no
change" against a state the clients never received.

⭐ **The failure is silent and self-erasing:** there is no retry, and the evidence that a broadcast was
missed is destroyed by the same statement that misses it.

## It is a shape, not a single line

The Planner found the identical ordering at **`:266`, `:279`, `:453-454`, `:502`** as well as `:477`.
⚠ **Fix the shape, not the instance** — a plan that repairs one and leaves four is worse than none,
because it makes the class look handled.

## Why this matters more than it looks

The clients affected are the ones that drive the whole console surface — radio state, now-playing,
volume. A missed delta does not show as an error; it shows as **a panel that is quietly out of date
until something unrelated changes and forces the next broadcast.**

That is the same family as `AUD-12` (a source stuck at `Ready` while audio plays) and `GV-12` (a panel
stuck on an error after the backend recovers): **state that stops tracking reality with nothing
reporting a fault.**

## Scope questions for the plan

1. **Is assign-after-await always correct here?** Moving the assignment after the `await` fixes the
   missed delta, but ⚠ **check for re-entrancy first** — if two updates can interleave, a late
   assignment can write a stale value over a newer one. Establish whether this service is serialised
   (a timer? a single hosted loop?) before assuming the swap is safe.
2. **What should happen on a genuine send failure?** Not advancing the cache means the next tick
   re-sends — which is probably right, but it also means a persistently failing client causes repeated
   full broadcasts. Say which is intended.
3. **Does `SendAsync` actually throw, or swallow?** If it already catches internally, the cache-advance
   may be unreachable and this row is a tidy rather than a fix. ⚠ **Establish that before writing a
   test that cannot fail.**
4. **Are all five sites the same shape?** They were found by pattern. Read each — one may be
   deliberately ordered that way for a reason the others are not.

## Verification

Unit-testable: make the send throw, then assert the **next** cycle re-broadcasts the same delta.
⚠ **Must fail first** — today the second cycle sees "no change" and sends nothing, so the test is RED
against `main` by construction. **Confirm that rather than assuming it.**

⚠ `CLAUDE.md` § *Test Timing*: this service is timer-driven. **Do not race a wall clock** — use the
injectable `TimeProvider` idiom (`EncoderHudService` is the worked example) and synchronise on the
observation, not on elapsed time.

Likely auto-mergeable — no hardware, no live-audio path, unit-testable. Confirm in the plan.
