## What changed

- **The dot is gone.** `.visualizer-conn-dot` (an always-visible 8 px green/red dot at the top-right of the
  picker header, from `PR 4`) is removed from the markup and the stylesheet. Nothing shows while connected.
- **While the visualization hub is not connected**, the canvas area shows, centred: a `link_off` icon
  (Radzen material icon, `--signal-amber`), **"Visualizer disconnected"** (mono uppercase, the type of BAND's
  "No scan yet"), and **"Reconnecting..."** (three dots, as the app's other reconnect copy). Amber rather than
  red because the hub reconnects by itself, so this is a wait, not a fault to act on — the same red/amber rule
  as `.gv-reconnect-banner` (`HANDOFF-bell-failure-surfacing.md:155`). "Reconnecting" is made true, not
  assumed: the retry policy never gives up, nothing in the UI stops the hub, and (review finding) a `Closed`
  the service did not ask for — a server close that disallows reconnect — now restarts the retry loop, where
  before `StartAsync` returned early and nothing ever reconnected.
- **Precedence:** skeleton (canvas not initialised) → BAND's own states → **disconnected** → "Waiting for
  audio data". Without it, "Waiting for audio data" would wait for something that cannot arrive.
- **Accessibility:** `role="status"`, `aria-live="polite"`; the element is rendered once per disconnection,
  so it is announced on the change, not per frame.
- **Stale frame:** on a connected → disconnected change the canvas is cleared, so the last frame does not sit
  under the state looking live; and "has received data" is reset, so after the reconnect "Waiting for audio
  data" shows until a new frame arrives rather than a blank canvas with no message (review finding).
- **The icon is `aria-hidden`.** It is a font ligature, so without that its name, "link_off", is text inside
  the live region and is announced — the first render showed the status reading "link_off VISUALIZER
  DISCONNECTED".
- **BAND does not show it (decided).** BAND reads `/api/radio/bandmap` and `/api/radio/state` over REST and
  subscribes to no hub stream, so a hub drop does not affect it; it already has its own API-failure handling
  (messages, kept map, idle cadence).
- **Plumbing:** `AudioVisualizationHubService` raises a new `ConnectionStateChanged` on first connect, a
  retry-loop connect, reconnecting, reconnected, closed and stop. Previously the panel learnt of a change only
  if something else re-rendered it. `IsConnectedOverride` is an `internal` test seam (bUnit cannot reach a
  live hub); production never sets it.

## Sibling found, not fixed here (pre-existing; candidate row)

**The visualization hub's subscriptions are one set shared by every browser circuit.**
`AudioVisualizationHubService` is a singleton (`Program.cs:412`), and `_activeSubscriptions` is a plain
`HashSet` that every panel adds to on subscribe and removes from on unsubscribe — and `Unsubscribe*Async`
also leaves the hub group on the one shared connection. So when any circuit's panel is disposed (a page
closed, or a reloaded page's old circuit expiring after `DisconnectedCircuitRetentionPeriod`), it removes the
stream every other open panel is still using.

Seen once while rendering this PR locally (2026-10-02): a page opened about a minute after an earlier test
browser closed showed the disconnected state, cleared it 1.8 s after the hub came back, and then sat on
"Waiting for audio data" — consistent with the retry loop replaying an empty set. A fresh page received
frames at once. The mechanism is read from code; it was not reproduced deliberately. On the kiosk the likely
trigger is a page reload: the old circuit's disposal, up to the retention period later, would stop the new
page's stream. Related to `UI-18` (a popover that never unsubscribes) — the same set, the opposite failure.
