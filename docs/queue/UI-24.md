# `UI-24` — text-entry dialogs are hidden by the on-screen keyboard

[← Builder Queue index](../BUILDER_QUEUE.md)

🟡 **P2 (owner UAT finding).** Filed 2026-10-01 by the coordinator from the `UI-20` panel UAT, check 5
(*"long-press a card → Rename / Delete"*):

> *"5 - passes, but the keyboard occludes the dialog."*

**Not a `UI-20` regression.** The Rename Preset dialog has been a centred overlay since #373
(2026-05-17); `UI-20` only made the long-press its entry point.

## Which keyboard

It is the **in-app keyboard**, `src/Radio.Web/wwwroot/js/virtual-keyboard.js`, not GNOME's. Chrome on
this box never sends `zwp_text_input_v3.enable()`, so the OS keyboard never opens for a web field
([`docs/uat/2026-08-03-osk-wayland-viability/REPORT.md`](../uat/2026-08-03-osk-wayland-viability/REPORT.md)
F-3). The in-app keyboard opens on `focusin` of any text-like `<input>` or `<textarea>`, is
`position: fixed; bottom: 0`, and **does not resize the page**. Chrome reports no viewport change either
(F-2), so `visualViewport` cannot be used to react to it.

Measured in Chromium at 1920×720: the keyboard's top edge is at **y = 348** (QWERTY) and **y = 360**
(numpad). Everything below is covered while it is up.

The only existing compensation was `body.keyboard-active .mud-overlay .mud-paper { translateY(-150px) }`
in `virtual-keyboard.css`. Nothing has rendered those MudBlazor classes since the move to Radzen, so it
matched nothing. It is removed.

## Fix — one shared rule, applied to every dialog with a text field

`design-system.css` §20a:

- **`.kiosk-entry-overlay`**: the hand-built overlay, `align-items: flex-start` with `padding-top:
  var(--sp-6)`, replacing five copies of an inline centred style.
- **`.kiosk-entry-card`**: `--surface-overlay` on `--surface-separator`, the tokens Radzen's own
  `.rz-dialog` uses here.
- **`.kiosk-entry-actions`**: the button row, with **58 px** buttons (the preset bar arrows' size).
- **`.rz-dialog.kiosk-entry-dialog`**: `top: var(--sp-6)` and `max-height: calc(100% - 2 * var(--sp-6))`.
  Radzen centres an absolutely positioned `.rz-dialog` inside a fixed flex wrapper, and a top offset
  overrides that.
  - **`.rz-dialog-wrapper:has(> .rz-dialog.kiosk-entry-dialog) { z-index: 9999 }`**: Radzen stacks
    its wrapper at 1001, under the fixed top bar (1100), which hid the anchored dialog's title and ✕.
    The mask is the wrapper's child, so it rises with it. The keyboard (10001) stays above.
  - **The body shrinks under the cap** (`.rz-dialog-content` becomes a flex column), so the file
    browser's own list gives up height and its footer stays on screen.
  - Call sites pass `CssClass = KioskEntryDialog.CssClass`, a constant in
    `Components/Dialogs/KioskEntryDialog.cs`.

**Always top-anchored, not only while the keyboard is up.** Moving the dialog when the keyboard opens
would slide it out from under the finger that just tapped the field.

**Where they land.** Measured after, at 1920×720 with the keyboard up:

| Dialog | Box | Field(s) | Buttons | Keyboard top |
|---|---|---|---|---|
| Panel: Set Frequency, Save Preset, Rename Preset | card 144–332 | 197–237 | 249–307 (58 px) | 360 / 348 / 348 |
| Radio page: Set Frequency, Save Preset | card 24–212 (full-screen overlay) | in the card | end 187 | 360 / 348 |
| File browser (System Config) | 24–660, title bar 25–75 on top | search 153–193 | footer below 348 | 348 |
| Save Playlist (queue view) | 24–390 | name 127–167, description 235–299 | 321–365, the top 27 px visible | 348 |

**Why the panel's overlays start at y = 144.** They are bounded by `.page-transition > *` (§17), whose
transform makes it the containing block for fixed-position descendants. They cover the whole content
area: measured box 0–1920 × 120–720.

**Anchoring Radzen dialogs below the top bar was tried first and measured.** At y = 144, Save
Playlist's description field sat under the keys: the 228 px between bar and keyboard is too short for
it. Hence the stacking fix above.

**Known limits:**

- The file browser's footer buttons, and the lower part of Save Playlist's, are under the keyboard
  while it is up. Every field is clear. Enter or ✕ on the keyboard uncovers the buttons.

## Not in scope, and why

In-page fields (System Config, the device friendly-name grid, the phone dev tray) are not dialogs.
Clearing them needs the page to scroll the focused field above the keyboard, which means changing
`virtual-keyboard.js` to reserve space and scroll. That is a different mechanism with its own risks, on
pages that are rarely used on the panel. Recorded here for the coordinator to file if wanted. No row is
minted.

## Tests

- `RadioControlPanelTests.TextEntryDialogs_AreTopAnchored_ClearOfTheKeyboard` (frequency, save, rename).
  Opened through the UI (frequency tap, ＋ SAVE, long-press → Rename). Each must use
  `.kiosk-entry-overlay` with no inline style, and the field and both buttons must be in the card.
- `TextEntryDialogPlacementTests`:
  - the §20a rules (top-anchored, not centred, the Radzen top offset, 58 px);
  - the dead MudBlazor rule stays gone;
  - the Radio page's two dialogs;
  - **a source guard.** Every `DialogService.OpenAsync<X>` call site, where `X`'s markup holds a text
    field, must pass `KioskEntryDialog.CssClass`. A future dialog fails the suite rather than opening
    under the keyboard.

  - the class dropped from System Config's file browser;

  - the Radzen wrapper left at 1001;

  - the class dropped again from both real call sites, against the rewritten guard.
