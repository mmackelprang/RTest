# `UI-12` — `RadioStateChanged` has no null guard, and adding one would silently drop a live broadcast

[← Builder Queue index](../BUILDER_QUEUE.md)

🔵 **P3.** Filed 2026-09-08 by the `UI-7` Builder as its `L-8`. **Pre-existing, identical on `main`
before and after `UI-7`, and deliberately left alone** — which is the interesting part.

## The asymmetry

`AudioStateHubService` raises its events through the fan-out seam `UI-7` shipped. Three of them —
the `Encoder*` events — guard their payload before dispatching. **`RadioStateChanged` does not**, and
its payload is declared non-nullable.

So the shape is inconsistent across sibling events on the same service, and the inconsistency is
invisible unless you read all fifteen raise sites together, which is exactly what `UI-7` did.

## ⚠ Why the obvious fix is wrong

**Adding `if (dto is null) return;` would silently drop a broadcast the panel receives today.**

The payload is typed non-nullable, so a null arriving there means something upstream already violated
its own contract — but the current behaviour *delivers* that event and the UI *handles* it. A guard
would convert a visible, working broadcast into a silent no-op, which is the same class of defect this
week has been spent removing: **a failure wearing the costume of correct handling.**

⛔ **So do not treat this row as "add the missing guard."** It is a question about which of two
inconsistent shapes is right, and the answer may be to **remove** the guards from the `Encoder*`
events rather than add one here.

## Scope questions for the plan

1. **Can the payload actually be null?** Trace every publisher of `RadioStateChanged`. If nothing can
   produce a null, the guards on the `Encoder*` events are the anomaly and this row is a
   simplification, not a fix.
2. **If it can be null, what does the UI do today?** Establish the *current* behaviour by test before
   changing it. If a null currently reaches a component and renders something wrong, that is a
   different and more serious row than an inconsistency.
3. **What do the `Encoder*` guards actually prevent?** They were presumably added for a reason. Find
   it — `git log -S` on the guard text — before deciding they are the ones to remove.
4. **Is there a third shape elsewhere?** `UI-7`'s census found fifteen raise sites; check whether any
   other event guards differently again.

## Verification

Whatever direction is chosen, it **must fail first**: write the test that pins today's behaviour,
confirm it is RED against the change, and green after. ⚠ **A test that merely asserts the guard exists
proves nothing about whether the guard should exist.**

Likely auto-mergeable — no hardware, no live-audio path, unit-testable. But ⚠ **if the answer turns out
to be "a null can reach the UI today", stop and re-tier**: that is a defect, not a consistency cleanup.

## Provenance

Found while `UI-7` routed all fifteen raise sites through the fan-out seam. The Builder documented it
at the site and **preserved the existing behaviour deliberately** rather than tidying it in passing —
correctly, since the tidy would have changed runtime behaviour inside a PR whose subject was the
dispatch mechanism.

## ⛔ CORRECTION 2026-09-09 — this row's stated REASON is false. Its conclusion survives.

**This row says a guard *"would silently drop a broadcast the panel receives today … the UI handles
it."* The UI does not handle it.**

- **`RadioControlPanel.razor:1053`** — `if (dto.RdsRelevantChanged)` — **throws NRE on null.**
  (`_radioState = dto` at `:1047` is safe; the very next statement is not.)
- **`NowPlayingPanel.razor:646`, `RadioPage.razor:337`, `AudioStateStore.cs:241`** all **wipe cached
  radio state to null and repaint** — blanking the frequency well, the signal meter and the STEREO
  badge.

⚠ **Since `UI-7`, that NRE is swallowed per-subscriber by `NotifyAsync`.** So today's null path is **a
swallowed exception plus a three-surface state wipe** — the exact *"failure wearing the costume of
correct handling"* this row invokes the principle **against**.

⭐ **The conclusion — "do not just add the guard" — survives. The reason does not.** A plan that
inherited the reasoning would have defended the right shape with an argument that collapses on first
contact with `:1053`.

## ⭐ The direction, and it is neither option this row posed

**Guard all four events — but move the check into ONE shared, logged helper above the fan-out, and make
the `On<T>` type argument nullable.**

The rule is derivable from declarations already in the file: **an event declared `Func<T, Task>` cannot
represent null, so a null must be rejected at the boundary; an event declared `Func<T?, Task>` treats
null as *data* and must pass it through.** Four events are the former. `NowPlayingChanged`,
`VolumeChanged` and `EventPlaybackChanged` are the latter — **null there means "nothing is playing."**

## Can a null reach the UI? No — so it stays P3

Enumerated by mechanism, not grep. The decisive step: **`RadioStateChanged` is a `public event` on a
NON-PARTIAL class** (`AudioStateHubService.cs:33`), so the *language* guarantees every raise site is in
that file — **there is exactly one, `:206`.** Server-side likewise one sender
(`AudioStateUpdateService.cs:478-479`), provably non-null. Zero strongly-typed hub clients, zero
`nameof`/constant indirection across all 20 `SendAsync` sites, no client-callable broadcast.

⚠ **What justifies guarding anyway:** the parameter arrives from a **JSON deserializer across a process
boundary**, where nullable annotations are erased. Null is unreachable because of `radio-api`'s current
source — **not because the type system enforces it.**

## ⛔ What the `Encoder*` guards were for: nothing

**Copy-propagated boilerplate.** Origin `2cc41567` (ENC-9a, #491) on **`VisualizationModeChanged` — an
event since deleted** by `01220d0c`. ENC-0/ENC-4/ENC-12 copied it verbatim. **No commit message states
a reason, and PR #491's thread has zero mentions of "null" or "guard."** Decisively: `db132192` did the
*identical* parameterless→typed-DTO transformation on `RadioStateChanged` in the same file **and added
no guard.** Neither shape was reasoned about.

## ⚠ Two traps the plan names

1. ⛔ **Do NOT put the check inside `NotifyAsync<T>`.** It is the obvious unification and would delete
   three copies — and would **silently drop every `NowPlayingChanged(null)`, stranding the dock on the
   previous track forever.** That is this row's feared defect, in the one place it could actually
   happen. `T` is erased there; **the guard must stay above the fan-out.**
2. ⚠ **The guard is unreachable from every test in the assembly today**, which revises "unit-testable".
   It lives inside the `_hubConnection.On<T>(…)` lambda, needing a started `HubConnection`; every
   fixture uses `OfflineHubTransport`. And `HubEventFire` fires the **event**, which is *downstream* of
   the guard — **a test through it passes whether the guard is present, absent or inverted**
   (`AudioStateHubServiceTests.cs:148-158` already says so). **So building the seam is the substance of
   this row**, not scaffolding. RED is shown by a four-mutation matrix including a control that must
   stay **green**.

**Auto-mergeable: yes** — Web + tests only. ⚠ **But narrowed: the change is unobservable in production**
(null cannot arrive), so UAT can only confirm no regression on the normal path. **A UAT report claiming
it demonstrated the guard would be wrong.**
