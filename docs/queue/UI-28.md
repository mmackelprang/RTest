# `UI-28` — Shuffle / Repeat switch themselves off while a file plays

[← Builder Queue index](../BUILDER_QUEUE.md)

🚧 **BUILT 2026-10-02, HELD for owner panel UAT** — [#765](https://github.com/mmackelprang/RTest/pull/765), branch `fix/ui-28-29-shuffle-band-tab`, one PR with
`UI-29` and `UI-30`. Not deployed (`AUD-85` deploys first).

🟠 **P1 (owner report).** Filed 2026-10-02 by the Builder.

> *"Shuffle / Repeat are deselected whenever the progress bar in file player updates."*

## Answer: the server lost the setting; the buttons were telling the truth

**Server-side, in `FilePlayerAudioSource`.** The UI (`NowPlayingPanel.RefreshPlaybackStateAsync`) copies
`isShuffleEnabled` / `repeatMode` from `GET /api/audio` on every `PlaybackStateChanged`, and that event
fires on every position change — so the "progress bar update" is just the first moment the panel re-reads
a value the server had already reverted. Repeat had genuinely stopped applying (the file player reads
`_preferences.CurrentValue.Repeat` at track end); for Shuffle the queue already reordered stays reordered,
but the flag and every later refill are back to unshuffled.

## Cause — measured

`FilePlayerAudioSource` kept Shuffle and Repeat **only** in `IOptionsMonitor<FilePlayerPreferences>.CurrentValue`
(`SetShuffleAsync` / `SetRepeatModeAsync` assigned to it and returned). That object is a cache:

1. Every `IConfigurationManager.SetValueAsync` in `radio-api` calls `ConfigStoreChangeNotifier.NotifyReload()`
   (`ConfigurationManager.cs:210`), which reloads `SqliteConfigurationProvider` and fires the change token.
2. The options monitor then rebuilds `CurrentValue` from configuration.
3. Configuration never held the new values: `PreferencesPersistenceService` writes `FilePlayerPreferences`
   to the store only every **30 s**. Any reload inside that window put Shuffle/Repeat back to their stored
   values.

The reload that hit the owner, from the box's file sink (EDT, 2026-10-01):

| Time | Event |
|---|---|
| 18:22:01.198 | `Shuffle set to true` |
| 18:22:02.303 | `Configuration section queue.state updated` |
| 18:26:30.514 / 33.455 | `Repeat mode set to "All"` / `Shuffle set to true` |
| 18:26:42.987 | `queue.state updated` |
| 18:26:51.414 / 53.918 | `Shuffle set to true` / `Repeat mode set to "All"` — **set again: the UI showed them off** |
| 18:27:01.620 | `queue.state updated` |
| 18:27:10.662 | `Shuffle set to true` — **a third time** |
| 18:27:19.998 | `queue.state updated` |

The owner turned Shuffle on three times in 40 s; the UI sends `!_isShuffleEnabled`, so each press means the
panel was showing it off. Each `queue.state` write is the Web queue panel's
`QueueHistoryPanel.ScheduleQueueSaveAsync` → `POST /api/configuration/queue.state` →
`ConfigurationController` → `SetValueAsync` → reload. It runs on every `QueueChanged` broadcast, and toggling
shuffle reorders the queue, so the toggle schedules its own undo. Every other `SetValueAsync` (volume
persistence, the Cast default, a System Config save) does the same.

## Fix

`SetShuffleAsync` and `SetRepeatModeAsync` now write `FilePlayerPreferences:Shuffle` /
`FilePlayerPreferences:Repeat` — **and every case variant of that key already in the table** — to the store
**before** assigning the cached value (`PersistPlaybackModeAsync`).

⚠ **The case variants are not a nicety; without them the fix does nothing on this box.** Found by the
pre-merge reviewer, then confirmed read-only on the box (`sqlite3 -readonly …/configuration.db`, 2026-10-02):

| rowid | Key | Value | Written |
|---|---|---|---|
| 11 | `FilePlayerPreferences:Shuffle` | `False` | 2026-10-01 (PreferencesPersistenceService) |
| 12 | `FilePlayerPreferences:Repeat` | `Off` | 2026-10-01 |
| 30 | `fileplayerpreferences:shuffle` | `false` | 2026-02-12 |
| 31 | `fileplayerpreferences:repeat` | `Off` | 2026-02-12 |

The lowercase rows come from the System Config page's File Player save: `ConfigurationController` lowercases
the section (`ConfigurationController.cs:364`). SQLite's `TEXT PRIMARY KEY` is case-sensitive, so both rows
live side by side; `SqliteConfigurationProvider` folds keys case-insensitively, so the row it reads **last**
wins — here the lowercase one, holding `false` / `Off`. This is also why `PreferencesPersistenceService`'s own
30-second saves never made Shuffle stick across a reload. Writing every variant makes the read order
irrelevant, and keeps the System Config page showing the live value. The write uses `IConfigurationStore.SetEntriesAsync`, which does not itself
reload (only `ConfigurationManager.SetValueAsync` calls `NotifyReload`), so it does not wipe the other values
still held only in `CurrentValue`. After it, a reload rebuilds `CurrentValue` **with** the new value. The
read path, the System Config page's Shuffle/Repeat defaults and `PreferencesPersistenceService` are
unchanged. A store failure is logged at Warning and the in-memory toggle still happens — the old behaviour.

**Residual windows, stated rather than hidden** (both milliseconds wide, not 30 s): a reload whose SQLite
read happened *before* this write and whose change token fires *after* it still rebuilds from the old value;
and `PreferencesPersistenceService` serialises `CurrentValue` before awaiting its own write, so a toggle that
falls between the two can be overwritten by that older snapshot.

**Not covered: the JSON store mode** (`CurrentStoreType != Sqlite`). There the write goes to the JSON
store's file, which is not the `config.json` the API's configuration watches, so nothing reads it back. That
is the pre-existing behaviour of `PreferencesPersistenceService` too; the box runs SQLite.

## Siblings found, not fixed here

- **The same pattern holds `SongPositionMs` and `LastSongPlayed`** (`FilePlayerAudioSource.cs` — assigned to
  `CurrentValue` in `StopCoreAsync` and `DisposeAsyncCore`). A reload between that assignment and the next
  30-second save loses the restart-restore position. Low impact; not filed.
- **`queue.state` is written and never read.** `QueuePersistenceService.RestoreQueueStateAsync` and
  `ClearQueueStateAsync` have no callers in `src/`; the API's file player already persists its own queue
  (`SaveQueueStateAsync`). So every queue change costs a configuration write **and a process-wide options
  reload** for data nothing reads. A candidate row for the coordinator; not filed.
