# `UI-14` — The three hub events where a dropped null is user-visible have no test seam, and the guard that would break them passes every gate

[← Builder Queue index](../BUILDER_QUEUE.md)

🟡 **P2.** Filed 2026-09-09 by the `UI-12` Builder, from its pre-merge review finding `M6`.
**Deliberately deferred out of `UI-12` rather than folded in** — it is a scope extension, not a
defect in what that row shipped.

## The inversion

`UI-12` extracted `internal On…MessageAsync` seams for the **four** hub events declared
`Func<T, Task>` — the ones whose payload is non-nullable — so a null rejection could be tested at
all. It deliberately left the **three** declared `Func<T?, Task>` alone, because they must pass null
through and needed no guard.

⭐ **That is exactly backwards from where the risk lives.**

| | Events | A regression here is | Test seam |
|---|---|---|---|
| `UI-12` covered | `RadioStateChanged`, `EncoderConnectionChanged`, `EncoderConfigStatusChanged`, `EncoderHudChanged` | **unobservable in production** — no producer can send null (`UI-12` §0.2) | ✅ built |
| Still uncovered | `NowPlayingChanged`, `VolumeChanged`, `EventPlaybackChanged` | ⭐ **user-visible** | ⛔ none |

## ⛔ The mistake that passes the entire suite

`UI-12` §0.5 (`C-404`) forbids putting the null check inside `NotifyAsync<T>`, because `T` is erased
there and it cannot tell a contract violation from data. That hazard is now fenced by a long comment
on `AcceptPayload`. **The comment is not a gate, and the realistic form of the mistake defeats it:**

- The **naive** move — delete the four `AcceptPayload` calls and add `if (arg is null) return;` to
  `NotifyAsync<T>` — **fails 4 tests**, because `NotifyAsync<T>` cannot name the event and the four
  `Assert.Contains(… Message.Contains("<EventName>"))` assertions break. ⭐ Those log-content
  assertions are load-bearing precisely here.
- The **realistic** move — *keep* `AcceptPayload` and *also* add a "defensive" null check inside
  `NotifyAsync<T>` — **passes every test in `Radio.Web.Tests` (1,172 including `UI-12`'s 8 new
  ones), and the rest of the solution**, while silently dropping every
  `NowPlayingChanged(null)`, `VolumeChanged(null)` and
  `EventPlaybackChanged(null)`.

⚠ **Why nothing catches it.** The only tests that fire a null on those events —
`NowPlayingDockTests.cs:248`, `SleepTests.cs:309` — go through `HubEventFire`, which reflects the
compiler-generated backing field and invokes subscribers **directly, downstream of `NotifyAsync`.**
**No test in the repo ever executes `NotifyAsync<NowPlayingDto?>(handler, null)`.** This is the same
shape as `UI-7` `C-213` and `UI-12` §0.6: a harness that reports success against a broken
implementation.

## What a dropped null actually costs, per event

Verified during `UI-12`'s pre-merge review — ⚠ **and note the three are NOT equivalent, which
`UI-12`'s first draft got wrong:**

| Event | What null means, by evidence | Cost of dropping it |
|---|---|---|
| `NowPlayingChanged` | ⭐ **Demonstrated** — clears the dock. `NowPlayingDockTests.cs:248` and `SleepTests.cs:309` fire null and assert on the result | the dock and panel strand on the **previous track, forever** |
| `VolumeChanged` | ⛔ **NOT "an absent snapshot."** `AudioStateStore.cs:204-213` **discards** it and still notifies; `NowPlayingPanel.razor:617-631` treats null as a **REST re-fetch trigger** (`RefreshPlaybackStateAsync()`); `MainLayout.razor` early-returns | suppresses the REST fallback — volume/mute readout goes stale |
| `EventPlaybackChanged` | Plausible (`AudioStateStore.cs:327-332` assigns it, clearing the snapshot) but ⚠ **no producer sends one** — the API always sends `new { … }` (`AudioStateUpdateService.cs:1087`) | unevidenced; do not overstate it |

## Scope

Small. Mirror `UI-12` Task 1 for the three nullable events: extract `internal
On…MessageAsync(T? dto)` methods, register them as method groups, and add the **pass-through**
assertion that no seam currently permits:

```csharp
hub.NowPlayingChanged += d => { received = true; seen = d; return Task.CompletedTask; };
await hub.OnNowPlayingMessageAsync(null);
Assert.True(received);   // the null MUST reach the subscriber
Assert.Null(seen);
```

⭐ **That is the RED gate for `UI-12` §0.5, and the only assertion in this family that could ever fail
for a reason a user would notice.**

## Verification

⚠ **It must fail first, and `UI-12` §0.6's trap applies unchanged: do NOT write it through
`HubEventFire`** — that fires the *event*, downstream of the fan-out, and would pass whether the
pass-through works or not. Drive the `internal` seam.

The discriminating mutation: add `if (arg is null) return;` to `NotifyAsync<T>` and confirm the new
pass-through tests go **red**. Today that mutation is green across the whole suite, which is the
entire reason for this row.

**Auto-mergeable: likely yes** — `Radio.Web` + tests only, no hardware, no live-audio path.
⚠ But like `UI-12`, **the change is not demonstrable on the box** — it adds a gate, not a behaviour.

### The false part

This row contrasts the four events `UI-12` covered (*"no producer can send null"*) with the three it
left (*"user-visible"*), which implies a producer **can** send null on these three. **None can.**

Each has exactly **one** server-side sender, all in `AudioStateUpdateService.cs` — `:281` (from
`BuildNowPlayingDto`, non-nullable return, single `new NowPlayingDto{…}` at `:700`), `:504`
(`new VolumeDto{…}`), `:1087` (`new {…}`) — and **`AudioStateHub.cs` contains no `SendAsync` and no
`Clients.` at all.** ⭐ **Both families are identical in reachability.**

### The real distinction, which is sharper than the one this row claimed

**Permanence of the failure.** `AudioStateUpdateService` broadcasts **only on a change**, so a
wrongly-dropped null is **never re-sent**: the dock and the sleep screen strand indefinitely. `UI-12`'s
failure mode repaints wrongly **once**. That — not reachability — is why the ungated three are the
worse half.

### Four more corrections, all verified against the code

1. ⛔ **`NowPlayingChanged` has FIVE direct hub subscribers, not four**, and they do **three different
   things** with a null: `NowPlayingDock:148-162` **clears**; `Sleep.razor:443-450` **clears** (track
   block and art); `NowPlayingPanel:593-606` **REST re-fetches**; `AudioStateStore:178-186` **keeps**
   the cached value and notifies anyway; `MainLayout:1173-1176` discards and re-renders.
   ⚠ **`Sleep.razor:13` injects the HUB as `AudioState`** — it is a direct subscriber, not a store
   one, which the alias hides. `UI-12`'s per-event notes list only four consumers.
2. ⛔ **`UI-12`'s dossier mis-cites `AudioStateHubServiceTests.cs:148-158`.** It claims that comment
   "already says" `HubEventFire` is downstream of the guard. **It says no such thing** — it says no
   test in the assembly can show a delivered `EventPlaybackChanged` message reaches the event with
   payload intact, and never mentions `HubEventFire`. ⚠ **And `UI-12` MADE that comment false**: the
   `On…MessageAsync` seam is exactly the harness it calls *"no in-tree precedent"*. **This row must
   rewrite it** — `CLAUDE.md` § *Pre-Merge Review* item 4 verbatim, the shape that left `TEST-2` open

3. ⛔ **ADR-033 miscounts.** *"`NotifyAsync<T>` already fans out all seven payload-carrying events"* —

4. ⚠ **Two of the three have ZERO null coverage of any kind.** The only two tests firing a null

### `EventPlaybackChanged(null)` stays unevidenced — and the plan did not invent a contract for it

No producer sends one. ⭐ **But its single subscriber does two things, not one**
(`AudioStateStore:327-332`): it clears `EventPlayback` **and** sets `_eventPlaybackBroadcastSeen` —
the flag that lets a broadcast beat the one-shot REST seed. **So a dropped null would leave a later,
staler seed free to win.** Recorded as *what one would do*, explicitly not as an expected event.

### ⛔ Six premises fell, and this row's own load-bearing claim was one of them

1. ⭐ **The PERMANENCE mechanism was refuted by the function it cited.** This row's `⛔ PLANNED`
   section said *"once `_lastNowPlaying` records the silence… never re-sent"*. Backwards twice over:
   `_lastNowPlaying` is assigned from `BuildNowPlayingDto`, which **cannot return null**, and
   `HasNowPlayingChanged` returns `true` **unconditionally** when either side is null
   (`AudioStateUpdateService.cs:537-540`), so a cached null would re-broadcast on the next **500 ms**
   poll — the one thing that would *not* be permanent. The real mechanism: the **server** caches the
   non-null "nothing is playing" DTO, the **client** dropped the null off the wire, and every later
   comparison finds no change. **Right conclusion, wrong reason — for the third row running.**
2. ⛔ **"`AudioStateUpdateService` broadcasts only on a change" is false of the service.** True for
   `NowPlayingChanged` (`:277`) and `VolumeChanged` (`:500`); **`EventPlaybackChanged` has no change
   comparison anywhere in its path.** And the two real guards are not equality tests — both return
   `true` when either side is null, so the first broadcast after start always goes out.
3. ⛔ **This row's own claim that "`UI-12` MADE that comment false" is wrong on both halves.** The
   comment's specific claim — no in-tree precedent for reflecting into **`HubConnection`'s handler
   table** — is *still literally true*; `HubEventFire` reflects the hub **service's** backing field.
   And `UI-12` never touched `EventPlaybackChanged`, so it could not have falsified a comment about
   that event. **`UI-14` is what falsifies it**, by a different route: extracting the handler body,
   which needs no harness at all. Rewritten to say the old reason was *wrong, not merely stale*.
4. ⛔ **`SeedEventPlaybackAsync` does not exist** — it is `AudioStateStore.EnsureEventPlaybackSeededAsync`.
   The plan invented the one member name it told the Builder to prefer over line numbers.
5. ⛔ **The census as planned could not meet its own requirement** — `Assert.Equal(IEnumerable, IEnumerable)`
   has no user-message overload, so the mandated remedy would have had nowhere to appear.
6. ⛔ **"A value type cannot be null"** — `typeof(int?).IsValueType` is **`true`**, so the census's
   filter would have silently dropped a future `Func<TimeSpan?, Task>`: green while the eighth event
   landed ungated, the exact failure the file exists to prevent.
