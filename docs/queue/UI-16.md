# `UI-16` — the voicemail progress bar cannot be dragged and is hard to hit

[← Builder Queue index](../BUILDER_QUEUE.md)

🟠 **P1.** Filed 2026-09-28 from the owner's Phase 1 sitting ([result](../uat/2026-09-28-phase1-console-checks/RESULT.md), check 1.6).

## What the owner saw

> *"Note that the progress bar on voicemails either doesn't allow dragging or is hard to grab. I wasn't able to test that."*

Voicemail playback itself passed the same check: it ducks the radio, and follows mute and master volume.
Only the seek half of `PHN-2` §3 U5 could not be exercised, which is why U5 has **still** never been
run as specified.

## Both halves are true of the code

- **No drag.** `src/Radio.Web/Components/Pages/VoicemailPlayer.razor:67-71`: the determinate
  `.vm-scrubber` (`role="slider"`) binds `@onclick="OnScrubberClickAsync"` and nothing else — no
  `pointerdown` / `pointermove` / `pointerup`. A drag delivers no events the component handles; at
  best the release registers as a click at wherever the finger lifted.
- **Hard to hit.** The only visible target is `.now-playing-dock-progress`, the thin dock bar,
  reused as-is. On a touch panel a tap has to land inside a few pixels vertically.

## Recommended shape

- Pointer events with **seek on release** — the owner's `AUD-28` ruling for the file-player seek
  bar (commit when the drag ends, no debounce) applies by analogy; say so in the PR so the two
  controls behave alike.
- A hit area of ~44 px tall wrapping the visible bar, and a visible thumb while dragging.
- Keep the indeterminate branch (`role="progressbar"`, unknown duration) exactly as it is.

## Verify

At the cabinet: `PHN-2` §3 U5 as written — start a voicemail over the radio, **drag** to a new
position and **tap** a new position; both must reposition the audio. Then archive U5 with this row.

## Shipped — branch `feat/aud-28-ui-16-seek-on-release` (2026-09-29, pending merge)

- The determinate `.vm-scrubber` is now the shared `SeekBar` built for `AUD-28`
  (`src/Radio.Web/Components/Shared/SeekBar.razor`, `wwwroot/js/seek-bar.js`): **pointer capture, drag
  or tap, committed on release — the `AUD-28` ruling applied by analogy, so the two controls behave
  alike.** No debounce; nothing is sent during the drag. The `vm-time` readout follows the finger.
- **Hit area 48 px** (`--touch-min`) around a 4 px track — up from 43 px. The old `padding: 20px 0`
  now applies only to the indeterminate branch. **Thumb:** 14 px when idle-but-seekable, 24 px with a
  glow ring while dragging.
- **Assumption (conservative):** the bar is `aria-disabled` and ignores input until this row has a
  playback id — the same no-op the tap-only scrubber had. No thumb renders while disabled.
- **Indeterminate branch unchanged** (`role="progressbar"`, "Unknown length").
- `js/voicemail-player.js` is **deleted**; its one function (`fractionFromEvent`) is now inside
  `seek-bar.js`.
- **Tests:** four new `VoicemailPlayerTests` counting `POST /api/audio/events/evp-1/seek`: drag → 0
  then exactly 1 on release; tap → 1; readout follows; before play → disabled, 0.
- **Verify at the cabinet:** `PHN-2` §3 U5 as written — drag and tap must both reposition the audio.
