# `UI-16` — the voicemail progress bar cannot be dragged and is hard to hit

[← Builder Queue index](../BUILDER_QUEUE.md)

🟠 **P1.** Filed 2026-09-28 from the owner's Phase 1 sitting ([result](../uat/2026-09-28-phase1-console-checks/RESULT.md), check 1.6).

## What the owner saw

> *"Note that the progress bar on voicemails either doesn't allow dragging or is hard to grab. I wasn't able to test that."*

Voicemail playback itself passed the same check: it ducks the radio, and follows mute and master volume.
Only the seek half of `PHN-2` §3 U5 could not be exercised, which is why U5 has **still** never been
run as specified.

## Both halves are true of the code

- **No drag.** `src/Radio.Web/Components/Pages/VoicemailPlayer.razor:67-71`: the determinate
  `.vm-scrubber` (`role="slider"`) binds `@onclick="OnScrubberClickAsync"` and nothing else — no
  `pointerdown` / `pointermove` / `pointerup`. A drag delivers no events the component handles; at
  best the release registers as a click at wherever the finger lifted.
- **Hard to hit.** The only visible target is `.now-playing-dock-progress`, the thin dock bar,
  reused as-is. On a touch panel a tap has to land inside a few pixels vertically.

## Recommended shape

- Pointer events with **seek on release** — the owner's `AUD-28` ruling for the file-player seek
  bar (commit when the drag ends, no debounce) applies by analogy; say so in the PR so the two
  controls behave alike.
- A hit area of ~44 px tall wrapping the visible bar, and a visible thumb while dragging.
- Keep the indeterminate branch (`role="progressbar"`, unknown duration) exactly as it is.
