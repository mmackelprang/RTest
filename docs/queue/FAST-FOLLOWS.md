- **SMS send contract reconciliation** — 🚫 **SUPERSEDED BY OWNER DECISION `D31` (2026-09-05): sending stays off permanently, and `GV-5` is PARKED.** The three axes below are **still accurate about the contract** and are kept verbatim as the reconstruction record — they are why a flag flip alone would have produced `400 invalid_number` on every send rather than working SMS. **They are no longer work.** *Original note:* ✅ **SCOPED AND QUEUED as GV-5** ([ADR-028](../../design/decisions/2026-07-30-gv-sms-send-contract.md)). The earlier note here framed this as a response-shape mismatch; investigating the as-built endpoint found it is **larger on three axes**:
  - **The request is wrong and fails 100% of sends.** Ours is `SendSmsRequest(string ThreadId, string Text)`; theirs is `SendSmsRequest(string ToNumber, string Text, string? ThreadId, string? ClientCorrelationId = null)`. We POST `{"threadId":…,"text":…}`; `ToNumber` binds **`null`**, their `PhoneNumberNormalizer.TryNormalize(null)` returns false, and the route returns **`400 invalid_number`** — in both reply and new-recipient mode. Send was never functional, only silent.
  - **The taxonomy is nine codes, not eight.** `invalid_text` (400) was missing from the list previously recorded here. Full set: `queued` (200) | `send_disabled` (409) | `rate_limited` (429) | `invalid_text` (400) | `invalid_number` (400) | `auth_unavailable` (502) | `upstream_error` (502) | `timeout` (504) | `error` (500).
  - **We never subscribe to the outbound echo channel.** Outbound messages are broadcast on **`SmsSent`**, never on `SmsReceived`. `PhoneHubService` does not handle it, so GV-3's optimistic→confirmed de-dupe in `PhonePage.OnGvSmsReceived` is **unreachable dead code** and the optimistic bubble would linger un-reconciled. RotaryPhone's poller also re-surfaces the message later with a **different `Id`** by construction, so exact-id matching cannot be the only tier — their own source calls the fuzzy `(text + counterparty + ≤120s)` match "REQUIRED, not optional."
  - **Their `EnableSmsSend=false` is not a blocker.** A dark server returns `409 send_disabled` with no GV call; GV-5 treats that as an **availability state, not a failed send** (no red bubble, no Retry — nothing was sent). Flipping `RotaryPhone:Gv:SendEnabled` remains a separate, later two-side decision; GV-5 ships with it `false`.
