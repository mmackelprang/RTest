# `AUD-102` — Bands, API and UI agree about AM and SW: one owner per frequency, a receivable flag, validated steps, SW shown in kHz

[← Builder Queue index](../BUILDER_QUEUE.md)

🟢 **P2, third all-band row.** Filed 2026-10-11 by the Planner. Everything below was read from code on `main`
`2a2893d2`.

## Goal

Once AM and SW play (`AUD-99`, `AUD-101`), every surface should describe them the same way: the band list, the
API, the panel, the Radio page, the band map text, presets and dialogs. A 5 kHz SW step must be visible as a
5 kHz step.

## Measured facts

**Bands**
- **AM and SW overlap at 1.600–1.710 MHz.** AM is 530–1710 kHz (`src/RTLSDRCore/Bands/BandPresets.cs:18-19`), SW
  is 1.6–30 MHz (`:50-51`). `FindBandForFrequency` (`:173-176`) is `FirstOrDefault` over `AllBands`, so AM wins
  the overlap by list order alone. The SW band therefore has 110 kHz that a frequency tune can never reach, and
  the 1610–1700 kHz expanded-AM channels are reachable as AM only by accident. Similar order-decided edges:
  30 MHz (SW/VHF), 108 MHz (FM/AIR), and all of VHF 30–300 MHz under FM/AIR/WB. These are correct today by
  order, so document and test them rather than change them.
- **AM steps lack 5 kHz.** `AllowedStepSizes` is {1, 9, 10} kHz (`:21`). SW is {1, 2.5, 5} kHz (`:53`) with a
  5 kHz default.

**Config**
- **`RadioOptions` AM step/min/max are dead config.** `MinAMFrequencyKHz = 520`, `MaxAMFrequencyKHz = 1710`,
  `DefaultAMStepKHz = 10` (`src/Radio.Core/Configuration/RadioOptions.cs:41,56,61`) are bound only by the System
  Config page (`src/Radio.Web/Components/Pages/SystemConfigPage.razor:471,481,484`) and the Web DTO
  (`src/Radio.Web/Models/ApiModels.cs:903-907`). No server code reads them. The receiver uses `BandPresets`
  (530 kHz). ⚠ **Correction to the 2026-10-11 survey:** `DefaultAMFrequencyKHz` is **not** dead. It is read by
  `RadioBandMemoryService.cs:183`. There are **no SW defaults** in `RadioOptions` at all.

**API**
- **No receivable flag.** `RadioBandModel` (`src/Radio.Core/Models/RadioBandModel.cs`) has no flag. It is
  projected from `BandPresets` by reflection in `RadioBandService.GetAvailableBands`
  (`src/Radio.Infrastructure/Services/RadioBandService.cs:27-52`). Only the band-map DTO knows (`Mappable`,
  `UnavailableReason`, from static constants: see `AUD-103`).
- **Step is not validated against the band.** `RadioController` delegates (`src/Radio.API/Controllers/RadioController.cs:233-241`)
  to `SDRRadioAudioSource.SetFrequencyStepAsync` (`SDRRadioAudioSource.cs:396-405`), which only rejects `<= 0`.
  Any positive step is accepted, including 7 Hz on FM.
- **No modulation or bandwidth endpoints.** `RadioController.cs` contains no `Modulation` or `Bandwidth` route.
  `IRadioControl.SetModulation` and the SSB demodulators (`src/RTLSDRCore/DSP/SsbDemodulator.cs`) cannot be
  reached from the API. That is optional future work (below), not this row.

**UI** (only AM is ever shown in kHz)
- `FrequencyFormatter.FormatFrequency/FrequencyValue/FrequencyUnit/GetDialogStep`
  (`src/Radio.Web/Components/Shared/FrequencyFormatter.cs:15-47`) use kHz for `"AM"` only. SW prints MHz with
  **2 decimals**, so 5.900, 5.905 and 5.910 MHz all render `5.90`/`5.91`. Its fallback ranges (`:61-70`, `:85-94`)
  are stale against the presets: SW 1.8, VHF 136–174, AM 520.
- The same AM-only rule appears in `BandMapText.cs:73,93,114`, `BandAxis.cs:97` (`IsKhz`),
  `RadioBandService.FormatRange` (`RadioBandService.cs:60-81`, MHz with `0.##` for SW), and the frequency-entry
  dialogs: `RadioControlPanel.razor:348,1683,1696` and `RadioPage.razor:173,381,398`.
- **The step list on the Radio page is static.** `RadioPage.razor:228-237` offers 1/9/10/25/100/200 kHz/1 MHz:
  no 2.5 or 5 kHz for SW, and it ignores the band. The control panel already uses the band's
  `AllowedStepSizes` (`RadioControlPanel.razor:2024-2026`).
- **Preset auto-names.** `RadioPreset.GetDefaultName` (`src/Radio.Core/Models/Audio/RadioPreset.cs:44-55`)
  formats the raw `frequency` with `F0`/`F1`/`F2`. The encoder saves with Hz
  (`PresetSelectorService.cs:522` passes `hz`), so an unnamed AM preset becomes `AM - 1000000` and an SW one
  `SW - 5900000.00`. Check the API path's units too (`RadioController.cs:651`).
- `SystemConfigPage.razor:2172`'s band list has no AIR. That is noted, not in scope.

## Scope

1. **Band edges.** SW starts above AM's top channel. Recommended: SW min **1.711 MHz**, or 1.8 MHz. The plan
   picks one and says why. `FindBandForFrequency` gets a test for each boundary (1.710/1.711 MHz, 30 MHz,
   108 MHz) so order-dependence is pinned rather than accidental. Add 5 kHz to the AM allowed steps only if the
   owner wants it; otherwise leave AM as is.
2. **One source for band ranges and defaults.** Delete the dead `RadioOptions` AM min/max/step and their UI and
   DTO fields, or make them real. Recommended: delete (greenfield, no backward compatibility, per `MEMORY.md`).
   Keep `DefaultAMFrequencyKHz`. Add an SW default frequency only if `RadioBandMemoryService` needs one; check
   what it does for SW today. ⚠ The config store may hold rows for deleted keys. Harmless, but say so in the PR.
3. **A receivable flag on `RadioBandModel`** (for example `IsReceivable` + `UnavailableReason`), computed from the
   **device's** capability (`AUD-99`'s HF decision and real `DeviceInfo` range). This must be the same source
   `AUD-103` gives the band map, so the panel and the BAND view cannot disagree. This also answers `AUD-94`'s data
   gap. **Do not build the dimmed-pill UI** (`AUD-94` option 1, preset-bar spec PR 4): the owner declined it on
   2026-10-02, and with the NESDR every band should be receivable. Expose the flag; the UI can use it later if a
   band is ever unreceivable again.
4. **Validate steps.** `SetFrequencyStepAsync` (or the controller) rejects a step not in the current band's
   `AllowedStepSizes`, as a 400 with the allowed list. Check every caller (encoder, panel, Radio page, restore at
   startup `SDRRadioAudioSource.cs:952-954`) for a step it might send that is now refused, especially a saved
   step from before a band change (`AUD-95`).
5. **SW in kHz everywhere** (recommended over 3-decimal MHz: SW listeners and schedules use kHz, and it removes the
   collision). One rule, `IsKhz(band) = AM || SW`, shared by `FrequencyFormatter`, `BandMapText`, `BandAxis`,
   `RadioBandService.FormatRange`, both entry dialogs and the frequency readouts. ⚠ The two-unit test helpers in
   `Radio.Web.Tests` will need updating; do not weaken their assertions. Measure on the 1920×720 panel that
   `5905 kHz` fits wherever `107.9 MHz` fits.
6. **Step lists from the band.** `RadioPage.razor`'s dropdown is built from the band's `AllowedStepSizes`, as the
   panel's already is.
7. **Preset names in display units.** `GetDefaultName` takes Hz and formats with the same rule (`AM - 1010`,
   `SW - 5905`, `FM - 101.5`). Fix the caller that passes non-Hz, if any. Existing presets are not renamed.

## Out of scope / future

- Modulation and bandwidth API endpoints (SSB for amateur SW, a narrow/wide AM switch): optional, not requested.
- AM station identity: there is no RDS on AM or SW. A station name for AM would need something else (a lookup
  table by frequency and location, or fingerprinting). Not requested. Add it to
  `docs/known-issues-and-future-work.md` with this row.
- The dimmed `UNAVAILABLE` pill UI (declined 2026-10-02).

## Implementation notes (Builder, 2026-10-12)

Built on `feat/aud-102-am-sw-bands-ui` on top of `main` `6c422e6` (`AUD-99`, `AUD-101`). Code commit `ab63d62`.
All anchors in § *Measured facts* were re-located; the corrections are under *Dossier claims found false* below.

**1. Band edge: SW starts at 1.711 MHz** (`src/RTLSDRCore/Bands/BandPresets.cs`, `Shortwave.MinFrequencyHz`).
Chosen over 1.8 MHz because it leaves no hole: with 1.8 MHz, a direct tune to 1711–1799 kHz finds no preset
band, falls to `TrySetFrequency`'s custom-band path, and fails as out of range (the tuner path's floor is
24 MHz), although the dongle receives it in HF mode. With 1.711 MHz every whole-kHz frequency from 530 kHz up
belongs to a band; only the sliver strictly between 1710 and 1711 kHz (e.g. 1710.5 kHz) is in none, and the
tests pin that too. The cost: the SW bottom edge is off the 5 kHz broadcast grid, so the band memory's
no-memory default (the bottom edge) is now rounded **up** to the band's default-step grid
(`RadioBandMemoryService.BottomEdge`): SW lands on **1715 kHz**; WB, AIR and VHF edges are already on their
grid and do not move. Edges pinned by `BandPresetsTests.FindBandForFrequency_AtTheBandEdges`: 1.600, 1.700 and
1.710 MHz → AM; 1.711 and 1.715 MHz → SW; 30 MHz → SW (order); 30.000001 MHz → VHF; 87.5 and 108 MHz → FM
(order); 108.000001 and 137 MHz → AIR; 162.4 and 162.55 MHz → WB (inside VHF, order); 300 MHz → VHF; and
529.999 kHz, 1710.5 kHz and 300.000001 MHz → no band. AM's step list is unchanged ({1, 9, 10} kHz; owner: no
5 kHz). `RTLSDRCore` 1.2.0 → 1.3.0 (new public `BandReception`, changed SW range).

**2. Deleted options.** `RadioOptions.DefaultAMStepKHz`, `MinAMFrequencyKHz`, `MaxAMFrequencyKHz`, their three
System Config fields, the three `RadioConfigDto` members, and their rows in `docs/configuration.md`.
`DefaultAMFrequencyKHz` stays (read by `RadioBandMemoryService`). ⚠ The box's config store may still hold rows
for the three deleted keys: harmless, nothing binds them. **SW today:** `RadioBandMemoryService` has no SW
default and needs none: with nothing remembered SW lands on the bottom edge, now 1715 kHz (above). Not deleted,
noted: `MinFMFrequencyMHz` / `MaxFMFrequencyMHz` are dead by the same test (no server reader), outside this
row's pinned scope.

**3. Receivable flag.** `RadioBandModel.IsReceivable` (default true) and `UnavailableReason`. One function,
`RTLSDRCore.Bands.BandReception.UnavailableReason(BandType, deviceMinHz, deviceMaxHz, cannot = "received")`:
null when the band's whole range is inside the device's, else the band map's sentence ending "cannot be
received". `BandSweepPlans.UnavailableReason(band)` now calls it with the tuner's fixed 24 MHz–1.766 GHz and
`cannot: "scanned"`, so the band map's text is byte-identical (pinned by `BandReceptionTests`); **`AUD-103`**
only has to pass the device's range instead. `RadioBandService` takes an optional `IRadioFactory` and uses
`GetSdrHardware()`: the in-use device, else the first enumerated one. **No device (tests, a dev box without a
dongle, or a factory that throws): every band is receivable.** The flag reports a device's limits; with no
device there are none to report, and the radio's absence is already reported elsewhere ("no tuner detected").
On a device without HF: `The AM Broadcast band (530–1,710 kHz) is below this tuner's 24 MHz lower limit and
cannot be received.` and `The Shortwave band (1.711–30 MHz) is mostly below this tuner's 24 MHz lower limit and
cannot be received.` No UI reads the flag (the dimmed pill was declined).

**4. Step validation.** `SDRRadioAudioSource.SetFrequencyStepAsync` throws the new
`Radio.Core.Exceptions.FrequencyStepNotAllowedException` (an `ArgumentOutOfRangeException`) when the current
band lists steps and the step is not one of them; a custom band (empty list) accepts any positive step.
`POST /api/radio/step` → **400** `{ error, band, allowedStepsHz }`, logged at Information (file sink, not the
journal). Callers checked:

| Caller | Can it send a refused step? |
|---|---|
| Encoder (`RotaryEncoderActionRouter`) | No: it only calls `StepFrequencyUp/DownAsync`. Nothing in `src/` but the controller calls `SetFrequencyStepAsync`. |
| Control panel step chip (`CycleStepSizeAsync`) | No: it cycles the band's `AllowedStepSizes`; an unlisted current step (AUD-95) gives index −1, so the first tap sends the band's first step. |
| Radio page dropdown | No: its options are now the band's `AllowedStepSizes`; the page reloads state after every set, so a refused step is not kept optimistically. |
| Start-up restore (`RestorePersistedRadioPreferencesAsync`) | It bypasses the setter. It now checks the saved step against the restored band and, if it is not allowed, uses the band default with **one Warning** (journal) per restore; while the radio is active the 30 s preferences loop then saves the default. |
| `AUD-95` path (frequency-only tune into another band) | **Not absorbed.** The old band's step is kept, as before. Nothing re-validates it, so nothing throws: stepping uses it (test: WB's 25 kHz kept on FM, step up → 101.525 MHz), and the next step change is validated against the new band (25 kHz refused, 100 kHz accepted). The panel chip shows the kept step and its first tap goes to FM's 50 kHz; the Radio page dropdown shows its placeholder. |

**5. SW in kHz: the rule and every file.** `Radio.Core.Models.Audio.BandUnits`: `IsKhz(string)` and
`IsKhz(RadioBand)` (AM or SW), `FormatKhz` (`0.#`: `5905`, `5907.5` for a 2.5 kHz step) and
`Format(band, Frequency)`. Used by:
- `FrequencyFormatter` (the readouts on the panel, the Radio page and the preset cards; dialog units,
  placeholder, step and min/max). Its fallback ranges now match the presets: AM 530–1710 kHz, SW
  1711–30000 kHz, VHF 30–300 MHz (were 520 kHz, 1.8 MHz, 136–174 MHz).
- `BandMapText` (`FormatRange`, `FormatFrequency`, `FormatStation`) and `BandAxis.IsKhz`.
- `RadioBandService.FormatRange` (the SW pill's range is `1711–30000 kHz`).
- Both frequency dialogs, `RadioControlPanel.razor` and `RadioPage.razor`, through
  `FrequencyFormatter.ToDisplayUnits` / `FromDisplayUnits` / `DialogPlaceholder`.
- The readouts that used `Frequency.ToDisplayString()`: `SourceSelectorService` (band row, context line),
  `RotaryEncoderActionRouter` (TUNING card, both sites), `PresetSelectorService` (rows, save notice, context
  line) and `PlayHistoryTracker` (source details). These printed SW 5.905 MHz as `5.9 MHz` and **AM 1010 kHz as
  `1.0 MHz`**.

MHz bands keep their old formats. Rendered: SW `5905 kHz` on the panel, the Radio page and the TUNING card;
FM `101.50 MHz` on the panel and the Radio page and `101.5 MHz` on the TUNING card, all unchanged.

**6. Radio page step list** is built from the band's `AllowedStepSizes` (labels by `FormatStep`: `1 kHz`,
`2.5 kHz`, `5 kHz` on SW). It is empty until the band list has loaded.

**7. Preset names.** `RadioPreset.GetDefaultName(band, frequencyHz)` takes hertz: `AM - 1010`, `SW - 5905`,
`SW - 5907.5`, `FM - 101.5`, and `0.000###` MHz on the other bands (`WB - 162.475`). Callers:
`RadioPresetService.AddPresetAsync` (blank name; reached from `POST /api/radio/presets`, whose Web callers send
`RadioStateDto.Frequency`, which is hertz) and now the encoder's save fallback (`PresetSelectorService.NameFor`,
which used to spell out `FM 101.5 MHz` / `SW 5.9 MHz` itself). No caller passed non-hertz. The panel's and the
Radio page's save dialogs keep their own editable seeds (`SW 5905 kHz`, `SW - 5905 kHz`). Stored presets are not
renamed.
