# `UI-18` — `GainControlPopover` subscribes to `Levels` and never unsubscribes

[← Builder Queue index](../BUILDER_QUEUE.md)

🟢 **P3.** Filed 2026-09-30 on the owner's ruling to queue the `UI-10` follow-ups ([`RETURN-CHECKLIST.md`](../uat/RETURN-CHECKLIST.md) §6: *"Ruled 2026-09-30: queue them"*). CPU saving, not correctness.

## The finding

`GainControlPopover` subscribes `AudioVisualizationHubService` (a singleton in `radio-web`) to the `Levels` group when it opens and never unsubscribes. After the popover has been opened once, `radio-web` stays in the `Levels` group until the process restarts, so the API keeps computing and sending level frames that nothing on screen shows.

## Scope questions for the plan

1. Where does the popover subscribe, and does it have a close/dispose path to unsubscribe from? Confirm by reading, do not assume.
2. Is `Levels` shared with another consumer (a visualizer showing levels)? The hub service is shared, so dropping the group on popover close must not cut off a surface that is still showing it — a reference count or per-consumer subscription may be needed.
3. The saving only reaches the API if `UI-19` makes the server's work depend on who is subscribed; check the two together.

## Verification

A bUnit or service-level test that opening and closing the popover leaves the `Levels` subscription as it found it. On the box, optionally: with the popover closed and no visualizer shown, `radio-web` is not in the `Levels` group.
