# `UI-34` — the Save Playlist dialog's fields ran past its right edge

[← Builder Queue index](../BUILDER_QUEUE.md)

🟡 **P2.** Filed 2026-10-02 on the owner's report, routed by the coordinator into the `UI-32` PR ("the current round of UX improvements"). **HELD for owner panel UAT — not deployed, not merged.**

## The report (owner, 2026-10-02, verbatim)

> *"One thing I noticed on the 'Save Playlist' dialog - the bounding boxes for the Playlist Name and 'Description (Optional)' flow past the right edge of the dialog. We should fix that in the current round of UX improvements."*

## Cause (measured in Chromium at 1920×720, local render of the current Web against a read-only proxy of the box API)

`SavePlaylistDialog.razor`'s form was `<div style="min-width: 400px;">`, inside a dialog the queue panel opens **400 px wide**. The dialog's content box is narrower than that by Radzen's padding (24 px a side), so the form — and both `width: 100%` fields in it — were wider than the box they sat in:

| | Before | After |
|---|---|---|
| Dialog | x 760, 400 wide | same |
| Content box, inner right edge | 1135 | 1135 |
| Content `scrollWidth` / `clientWidth` | **448 / 398** (overflowing) | 398 / 398 |
| Playlist Name input | 761 → **1161**, 400 wide | 785 → 1135, 350 wide |
| Description textarea | 761 → **1161**, 400 wide | 785 → 1135, 350 wide |

Both fields ended **26 px** past the content box's right edge, and the overflowing content had scrolled sideways so they also lost their left padding. The same with the in-app keyboard up (its top edge at y = 348): identical numbers before and after. Screens: `ui34-before-save-playlist.png`, `ui34-before-save-playlist-keyboard.png`, `ui34-after-save-playlist.png`, `ui34-after-save-playlist-keyboard.png` (scratchpad `ui32-screens/`).

`UI-24` (#761) did not introduce it — the `min-width` predates the top anchoring — but anchoring the dialog where the owner now looks at it while typing made it visible.

## Fix

The form drops the fixed width and takes `.save-playlist-form` (`width: 100%; min-width: 0`), and its text box and text area are `width: 100%; max-width: 100%; box-sizing: border-box` (`design-system.css`, § UI-32 / UI-34). The dialog is still opened 400 px wide.

## Tests

- `TextEntryDialogPlacementTests.SavePlaylistDialog_FormFillsTheContentBox_AndItsFieldsAreFullWidth` — the form carries the class and no inline size; both fields are `width: 100%`.
- `…Css_SavePlaylistForm_FillsItsDialog_WithBorderBoxFields` — the stylesheet rules.
- `…NoDialogComponent_PinsItsContentToAFixedPixelMinWidth` — a scan of `Components/Dialogs/*.razor` for an inline `min-width: Npx` (N ≥ 1); `min-width: 0` is allowed. This is the class of mistake, not just this instance.

bUnit computes no layout, so these pin the cause; the geometry above is the evidence the fix works.
