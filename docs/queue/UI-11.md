# `UI-11` — an unmatched `/api/*` path returns HTTP 200 and `index.html` instead of 404

[← Builder Queue index](../BUILDER_QUEUE.md)

🟡 **P2.** Filed 2026-09-08. Offered by us to RotaryPhone and **they asked for it** — *"Yes, please"* —
and they are filing the symmetric fix on their side, so the correction is two-way rather than one-sided.

## The defect

`Radio.Web`'s SPA fallback catches **everything** that does not match a route, including paths under
`/api/`. So a caller that asks for JSON at a mistyped or renamed API path gets:

- **HTTP 200**
- `Content-Type: text/html`
- the SPA shell

⭐ **It is the same disease as everything else both repos have spent this week unpicking: a success
code covering a failure.** `Succeeded: true` meaning only "the JSON parsed"; `available: true` during a
total outage; `NRestarts=0` on a unit being cycled; a falsification step that swapped two disjoint
types. **A 200 that is HTML when the caller asked for JSON belongs on that list.**

## It has cost real time twice in one day, on both sides

1. **Ours** — the original `XR-2` workaround. We tried a raw `/` in a thread id, which missed the API
   route entirely and fell through to the SPA fallback, **returning `index.html` with HTTP 200**. That
   made a broken request look like a successful one and sent the investigation sideways.
2. **Theirs** — 2026-09-08, verifying the `XR-2` fix *for us*, they probed `/api/gvsms/` instead of the
   real prefix `/api/gvbridge/sms/` and **got a 200 back with our SPA shell.** Their words: *"your
   SPA-fallback trap biting us in our own house."*

## What to build

An explicit terminal 404 for unmatched paths under `/api/` — before the SPA fallback, not after.

⚠ **Get the ordering right.** The fallback is a catch-all by design; the fix is a route or middleware
that claims `/api/{**rest}` and returns a 404 (ideally `application/json` with a small problem body),
registered so that **real API routes still win** and only genuinely unmatched ones reach it.

⚠ **Do not break the real fallback.** Deep links into the SPA (`/phone`, `/system`, `/radio`, …) must
still serve `index.html`. A fix that returns 404 for those is worse than the bug.

⚠ **Check the streaming endpoints.** `/stream/audio` and `/stream/audio/mp3` are not under `/api/` and
must not be caught by any new rule. Confirm what other non-`/api/` server routes exist before choosing
the prefix — a rule written for `/api/` only is safest, and widening it later is cheap.

## Scope question

**Is this `Radio.Web` only, or `Radio.API` too?** `Radio.API` serves no static files (per `CLAUDE.md`,
which is why `OPS-5` needed no equivalent there), so it probably has no SPA fallback to fix — but
**verify rather than assume**, and say which services were checked.

## Verification

Directly testable and **must fail first**: request `/api/definitely-not-a-route` and assert **404**,
not 200-with-HTML. Against `main` today that returns 200, so the test is RED by construction — confirm
it rather than assuming.

Pair it with a test that a real SPA deep link **still** returns `index.html`, so a future fix cannot
close this by breaking the fallback. **The pair is the point**: one assertion alone can be satisfied by
a change that makes the app worse.

Likely auto-mergeable — no hardware, no live-audio path, unit-testable in both directions.
