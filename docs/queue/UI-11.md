## ⛔⛔ THE BUILDER'S OWN "CORRECTION" WAS FALSE, AND PRE-MERGE REVIEW CAUGHT IT

Mid-cycle the Builder struck the plan's §6.3 (*"a wider pattern is how the console goes black"*) as
false, on a mutation that came back **20/20 green**, and wrote that conclusion into **four places** —
a test's XML doc, the plan, this dossier and two commit messages. **The reviewer refuted it from
framework source before the PR opened, and the re-measurement confirmed the reviewer.**

**§6.3 is TRUE.** Re-run over the **whole test project** instead of one class: **7 failed / 1,197
passed.** All four `StaticAssetPipelineTests` cases go RED, `/css/design-system.css` returning
`NotFound` instead of `OK`.

**The mechanism. The asymmetry is the crux: page routes are endpoints, static files are not.** A real
`@page` endpoint *competes* with the fallback and wins — on **route precedence first** (a literal
segment beats a catch-all, settling it before `Order` is consulted at all) and on `Order` second.
That half surviving is why the green reading looked plausible. ⚠ **`Order = int.MaxValue` is not what
protects those routes** — precedence already did, so an `Order`-only change would look safe and would
not be. **Static files never enter that competition.** The automatic `UseRouting()` is inserted
*before* all user middleware, so routing selects the fallback; then `StaticFileMiddleware` (user
middleware, `Program.cs:599`) **stands down purely because *some* endpoint is already selected**. And
`{**rest}` carries no `:nonfile` constraint — that exists only in `MapFallback`'s *default* pattern,
which this app does not use.

**Measured vs derived:** the CSS, the JS and the DSEG font are **measured** 404s (they are the three
`InlineData` cases). The Radzen theme and **`_framework/blazor.web.js`** going the same way — and so
the circuit never starting, leaving an unstyled, non-interactive shell on a 1920x720 wall panel — is
**derived** from the fact that one `UseStaticFiles` call serves them all. Sound, but derived.

⭐ **Why it happened, which is the reusable part.** The mutation was run as
`dotnet test --filter "FullyQualifiedName~ApiNotFoundPipelineTests"` and reported as *"the entire
suite"*. **20 is exactly that one class's case count.** The guard existed the whole time in the same
project — in `StaticAssetPipelineTests`, **the very file this row's own Task 1 had moved an hour
earlier.** Same shape as `KIOSK-3`'s *"our 'zero consumers' grep was scoped to `src/`; the consumer is
a shell script."*
⚠ **Two earlier mutations had each failed exactly their own test, and that is what made the third feel
safe. A positive control validates the INSTRUMENT, never the SEARCH SPACE.**

✅ **One genuine finding survives the retraction.** The narrow scope has a **second, independent**
reason nobody had written down: **truthfulness.** `/some-typo` is a mistyped *page*, and a `/{**rest}`
rule answers it *"No API route on this service matches the request path"* — a well-formed body
carrying a wrong answer, the row's own thesis one layer along. Nothing pinned that.
**`UnmatchedNonApiPath_DoesNotGetTheApiProblemBody` is kept** and pins it; `StaticAssetPipelineTests`
already pinned availability. Both reasons hold; they are different failures.

## ✅ The `UseStatusCodePages` trap (§6.1) was MEASURED in both directions — the protection is real

§6.1 is the strongest argument for having shipped Option B rather than tests alone, and it was
asserted rather than demonstrated. Both directions now measured:

| Mutation | Result |
|---|---|
| `UseStatusCodePages()` added, terminal rule **present** | **24/24 green** — the middleware left the response alone; still `application/problem+json` |
| `UseStatusCodePages()` added, terminal rule **removed** | `404` **`Content-Type: text/plain`**, body `Status Code: 404; Not Found` — middleware injected a body into a response the API contract owns |

**Mechanism:** `StatusCodePagesMiddleware` only fires on a response with **no body and no content
type**. Giving `/api/*` a body of its own is what forecloses it. Point the middleware at a Razor page
instead of the default and that `text/plain` becomes `text/html` — **the reported bug, through the
front door, with every pre-`UI-11` test still green.**

Also verified against Microsoft's own .NET 10 documentation rather than inherited from the plan:
*"The `NotFound` render fragment (`<NotFound>…</NotFound>`) isn't supported in .NET 10 or later."*
The supported replacement is the `Router.NotFoundPage` parameter, which this app does not use and
does not need — its unmatched-path behaviour is answered in the ASP.NET Core pipeline.

⛔ **Do not add `UseStatusCodePagesWithReExecute`** — see the plan §6.1 and `CLAUDE.md`.

## The defect

`Radio.Web`'s SPA fallback catches **everything** that does not match a route, including paths under
`/api/`. So a caller that asks for JSON at a mistyped or renamed API path gets:

- **HTTP 200**
- `Content-Type: text/html`
- the SPA shell

⭐ **It is the same disease as everything else both repos have spent this week unpicking: a success
code covering a failure.** `Succeeded: true` meaning only "the JSON parsed"; `available: true` during a
total outage; `NRestarts=0` on a unit being cycled; a falsification step that swapped two disjoint
types. **A 200 that is HTML when the caller asked for JSON belongs on that list.**

## It has cost real time twice in one day, on both sides

1. **Ours** — the original `XR-2` workaround. We tried a raw `/` in a thread id, which missed the API
   route entirely and fell through to the SPA fallback, **returning `index.html` with HTTP 200**. That
   made a broken request look like a successful one and sent the investigation sideways.
2. **Theirs** — 2026-09-08, verifying the `XR-2` fix *for us*, they probed `/api/gvsms/` instead of the
   real prefix `/api/gvbridge/sms/` and **got a 200 back with our SPA shell.** Their words: *"your
   SPA-fallback trap biting us in our own house."*

## What to build

An explicit terminal 404 for unmatched paths under `/api/` — before the SPA fallback, not after.

⚠ **Get the ordering right.** The fallback is a catch-all by design; the fix is a route or middleware
that claims `/api/{**rest}` and returns a 404 (ideally `application/json` with a small problem body),
registered so that **real API routes still win** and only genuinely unmatched ones reach it.

⚠ **Do not break the real fallback.** Deep links into the SPA (`/phone`, `/system`, `/radio`, …) must
still serve `index.html`. A fix that returns 404 for those is worse than the bug.

⚠ **Check the streaming endpoints.** `/stream/audio` and `/stream/audio/mp3` are not under `/api/` and
must not be caught by any new rule. Confirm what other non-`/api/` server routes exist before choosing
the prefix — a rule written for `/api/` only is safest, and widening it later is cheap.

## Scope question

**Is this `Radio.Web` only, or `Radio.API` too?** `Radio.API` serves no static files (per `CLAUDE.md`,
which is why `OPS-5` needed no equivalent there), so it probably has no SPA fallback to fix — but
**verify rather than assume**, and say which services were checked.

## Verification

Directly testable and **must fail first**: request `/api/definitely-not-a-route` and assert **404**,
not 200-with-HTML. Against `main` today that returns 200, so the test is RED by construction — confirm
it rather than assuming.

Pair it with a test that a real SPA deep link **still** returns `index.html`, so a future fix cannot
close this by breaking the fallback. **The pair is the point**: one assertion alone can be satisfied by
a change that makes the app worse.

Likely auto-mergeable — no hardware, no live-audio path, unit-testable in both directions.

# ⛔⛔ RETRACTED 2026-09-09 — `Radio.Web` HAS NO SPA FALLBACK, AND NEVER HAD ONE

**This row was filed on a false premise, and the premise was ours.** The bug is real; it is
**RotaryPhone's**, on `:5004`, and both incidents happened there.

## Six independent checks

| Check | Result |
|---|---|
| Live request to `radio-web`, unmatched `/api/*` | **`HTTP/1.1 404`, `Content-Length: 0`**, no `Content-Type` |
| `MapFallback` / `MapFallbackToPage` / `MapFallbackToFile` / `UseSpa` / `UseDefaultFiles` / `UseStatusCodePages*` in `src/` | **0 hits** |
| `git log -S "MapFallback" --all -- src/` | **0 commits** before this row's own fix — not removed, **never existed** (one hit today: `UI-11`'s terminal 404) |
| Any `*.html` under `src/Radio.Web/` | **none** — there is no `index.html` to return; the shell is generated from `Components/App.razor` |
| Any `@page` with a catch-all | **none** — twelve plain literal routes |
| `MapRazorComponents` (.NET 10) | one endpoint per `@page` plus `/_blazor*` — **no catch-all** |

The behaviour described belongs to the **legacy .NET 6/7 `MapFallbackToPage("/_Host")`** model, whose
`{*path:nonfile}` pattern produces exactly that `200`. **This app was never on it.**

## Both incidents were on RotaryPhone's `:5004` — and our own archive said so

⭐ **`docs/BUILDER_QUEUE_ARCHIVE.md:99`** records the original `XR-2` raw-slash probe falling through to
***"their** SPA fallback"*, and the route under test — `/api/gvbridge/sms/threads/…` — **only exists on
RotaryPhone.API.** Their own words were *"biting us **in our own house**"* and *"**Ours has the same
hole** and we are filing it on our side too."*

⭐ **The row is an instance of the disease it names.** A misattribution survived two hops — they said
"your trap", we recorded "ours", and **neither side re-derived which server sent the bytes.** The
refuting evidence was at line 99 of our own archive the whole time. **RotaryPhone has been told**;
their fix stands, only the ownership was wrong.

## ⛔ Three corrections to this row's technical framing

1. **"Ordering is the whole job" is wrong.** Endpoint selection is by **precedence then `Order`**, never
   `Map*` sequence; `MapFallback` stamps `Order = int.MaxValue` and file position is readability only.
   ⚠ **A Builder reasoning from the old model would hunt for a fallback to precede, find none, and
   improvise.**
2. **`/stream/audio*` are `Radio.API` routes** (`ApiPaths.cs:19-20`, `AudioStreamMiddleware.cs:112`).
   `Radio.Web` has none. `/api/`-scoping is still right, but because of the **eleven non-`/api/` page
   routes on this service**, not the streams.
3. **`Radio.API` is unaffected AND already locked** — `tests/Radio.API.Tests/ApiTests.cs:32-43` asserts
   `/api/nonexistent` → 404 and is green in CI. **Two services exist and both were checked.**

## What is genuinely worth shipping — the lock, not the fix

1. **The 404 has no body and no `Content-Type`.** That is the part that actually cost RotaryPhone a probe.
2. **Nothing locks the behaviour** — it is correct by accident of the hosting model, not by contract.
3. ⛔ **`Routes.razor:6-10` has a `<NotFound>` fragment that has NEVER been served** and is unsupported
   on .NET 10 — **markup asserting behaviour the code does not have**, exactly what `CLAUDE.md`
   § *Pre-Merge Review* exists to catch.

## ⚠ The trap that makes this worth doing at all

**`UseStatusCodePagesWithReExecute("/not-found")`** is what the .NET 10 Blazor Web App template now
ships, and what current Microsoft docs steer you to. **It would give every `/api/*` 404 an HTML body —
most of this row's original bug arriving through the front door, with every existing test green.**
Once `/api/*` has an explicit body, status-code pages cannot claim it.
