## What it does (spec §4.8)

While the PRESETS knob's overlay is open (the turn before the press):

- the bar **scrolls the highlighted card into view**;
- that card gets the overlay's highlight treatment — `--surface-hover` fill and a **2 px amber bar along
  the card's bottom edge** (the horizontal form of `.encoder-selector-bar`, `--row-accent` =
  `--source-radio`);
- when the overlay closes, the highlight clears and the bar returns to the active card (subject to
  `UI-20`'s 10 s manual-scroll hold-off).

Tapping a card while the overlay is open recalls that card; the overlay closes on its own idle timer. No
announcement is added — the HUD already has a `role="status"` mirror.

## ⚠ For the Planner to confirm — do not inherit

The spec *believes* the Web already receives everything needed: the full row list and `HighlightIndex`
in the HUD payload (`PresetSelectorService.cs:626-652`; row ids `preset:{id}`, `:336`). It asks the
Planner to confirm that `EncoderHudService` exposes that payload to **a second subscriber** (the bar, in
addition to the HUD). **That is a belief, not a measurement.** Read the delivery path end to end before
planning; if an API or hub change is needed, escalate to the Architect rather than widening this row.

### ✅ Answered by the Builder, 2026-10-01: the belief holds, and no API or hub change is needed

The delivery path was read end to end:

`PresetSelectorService.ComposeLocked` puts every row plus `HighlightIndex` into every publish. From there:

1. `EncoderFeedbackService` coalesces.
2. `AudioStateUpdateService.OnEncoderHudChanged` forwards `Rows` and `HighlightIndex` on SignalR `EncoderHudChanged`.
3. `AudioStateHubService.OnEncoderHudMessageAsync` receives it.
4. The Web's **`EncoderHudService`** singleton (`Program.cs:425`) holds it as `.Current` and raises `StateChanged`.

`StateChanged` is a multicast event, so the bar is a second subscriber beside `EncoderHud.razor`, reading the very object the overlay draws. Two consequences are now documented on both sides:

- **The match is by preset id.** Knob row ids are `preset:{RadioPreset.Id}`, the same `Id` that `GET /api/radio/presets` returns. That prefix is a wire contract: `PresetSelectorService.PresetIdPrefix` ↔ `PresetBar.KnobPresetRowPrefix`.
- **The DTO comment was wrong after this change.** It said the row id was "opaque to the Web", and was corrected.

## Build record — 2026-10-01 (Builder, PR [#758](https://github.com/mmackelprang/RTest/pull/758), ⛔ held, stacked on `UI-20`)

**What shipped:**

- `PresetBar.razor` subscribes to `EncoderHudService`.
  - `KnobPresetIdOf` reads the highlighted `preset:` row in the two phases where the overlay draws the list with a highlight (`SelectorPreview`, `SelectorBlocked`).
  - The bar re-renders only when the knob's preset id changes.
- `ChooseReveal` gains two rules:
  - while a knob card is mirrored, reveal it on each move. This is **not** subject to the 10 s hold, because turning the knob is itself browsing;
  - when the knob's list goes, return to the band target, unless the hold is running.
- CSS: `.rcp-bar-item.is-knob-highlight`. The `--surface-hover` wash is layered as an image, and a 2 px `--source-radio` bar sits at `bottom: 3px`, clear of the amber border on the playing card.

**Order:** band name, then per-band slot. Pinned from both sides by tests with the same six presets, with bands chosen so name order and enum order disagree.

**Evidence:**

- **Gates on head `926c25c3`:** 46/0. Full suite green apart from the six known `SrcVariableResamplerTests` and the NWS integration test.
- **Mutation checks: 12 of 12 killed.** Three were killed only by tests added for them. One survived at first (`band:FM` is exactly prefix-length) until the test was strengthened.
- **Pre-merge review:** 2 MEDIUM, fixed.
  - Turning onto a row the bar has no card for bounced the strip back to the playing preset mid-turn. The return is now keyed on the list closing.
  - A comment claimed Preview was the only list phase.
- **Polisher:** 1 MEDIUM, fixed. The knob bar fused with the playing card's amber border.
- **Static render** of the real markup and CSS: a local visual pre-check, not UAT.

**Owner checks at the panel, after the deploy step puts this branch on the box:**

1. Turn the PRESETS knob: the mark moves in step, across band boundaries, and off-screen cards scroll in.
2. Stop turning: on idle dismiss the mark clears and the strip returns to the playing preset.
3. Swipe the strip, then let the overlay close within 10 s: the strip stays put.
4. Rest the knob on the playing card: both cues show.
5. **Spec reading:** when the overlay swaps the list for "Switching to X…", the mark clears then, not when the overlay closes.
6. **Unverified risk:** spin the knob fast, then confirm the strip still returns on close. If an interrupted smooth scroll fires `scrollend`, the 10 s hold could be armed by mistake.

## Verification

- bUnit / service test: a HUD payload with a `HighlightIndex` pointing at a preset row highlights the
  matching card and scrolls it into view; overlay close clears it.
- Owner at the panel: turning the PRESETS knob moves the bar's highlight in step, and the card the knob
  lands on is the one the bar shows.
