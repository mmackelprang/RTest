## ⚠ The cause was NOT proven

The panel could not be powered off or the console put to sleep to reproduce it — the owner was using the
console, and the box is read-only for this row. Everything below was measured read-only, from the API and Web
file sinks, the user journal, and the kiosk's own Chrome over CDP `:9223` (`Runtime.evaluate` only; no
navigation, click or reload). It rules several candidates out and leaves the cause open. **The fix is a set of
guards plus an instrument that will say which side the next pause is on.**

### Measured

1. **While the panel is dark, the kiosk's Chrome renders nothing, but its scripts keep running.** The page's
   Long Animation Frame timeline (buffered, read 2026-10-02 14:37Z) holds one frame per deep sleep the owner
   ran on that page: started **14:30:27.355Z**, rendering began **6817 ms** later; started **14:31:08.052Z**,
   rendering began **6637 ms** later. The API log puts those deep sleeps at `10:30:27.327` → panel lit
   `10:30:34.062`, and `10:31:07.972` → panel lit `10:31:14.512` (local). So each frame spans the dark period
   and ends within ~0.2 s of the panel coming back. `blockingDuration` was **0** for both, and the frames'
   scripts were Blazor's `DOMWebSocket.onmessage` — the main thread was free and processing messages.
2. **`document.visibilityState` stayed `visible`.** The buffered `visibility-state` timeline has one entry,
   `visible` at page load (14:28:39Z). The page is never told it is hidden, so hidden-page timer throttling,
   `visibilitychange` and Chrome's freezing are **not** involved.
3. **The visualization hub never dropped.** `web-20261002.txt` has no `Reconnecting`, `closed` or re-subscribe
   line during the UAT window (10:26–10:35), so the hub's reconnect backoff (0/2/5/10/30 s) was not in play.
4. **Every panel power command succeeded first time.** `MutterPanelPowerControl` logs a Warning on any
   failure or timeout and there is none, so `PanelPowerService`'s power-on retry (5 s, then 10 s) was not in
   play either.
5. **The server side does not pause.** Read from code (subagent, verified file:line): the local playback
   device paces the mixer even while casting (`SoundFlowAudioEngine.cs` ~378-386, 1130-1182); mute sets
   `MasterMixer.Volume = 0` after the taps; sleep pauses the source and wake resumes it; nothing on that path
   stops, restarts or buffers the visualization tap.
6. **The kiosk was relaunched at 10:28:36**, 28 s after the 10:28:08 deep-sleep wake (`radio-kiosk.service`
   in the user journal). Whether that was the owner reacting to a pause is not known.

### What is left, and what this row does about it

The two measured deep sleeps both resumed rendering within ~0.2 s of the panel, so a frozen visualizer after
one is not explained by the browser's frame pipeline as measured. Three mechanisms remain that fit
"sometimes" and "resumes on its own", and each is now guarded:

| Mechanism (unproven) | Guard in this PR |
|---|---|
| The new Home page's `VisualizerPanel` drew its one start-up frame (`RequestInitialData`) and attached its live frame handlers only **after** two HTTP reads (`LoadPreferencesAsync`, `RefreshRadioActiveAsync`); radio-api is at its busiest at a wake (source resume, Cast unmute, three output-settings reloads in the log). A slow read = a frozen frame for its duration. | Handlers attached **before** the reads. Test: `ALiveFrame_IsDrawn_WhileThePreferencesReadIsStillInFlight`. |
| `AudioVisualizationHubService` awaits each subscriber in turn, and each panel's handler awaited its browser round trip, so any slow browser held the one shared stream and then drained a queue of stale frames one round trip at a time (a burst of 8 frames in 76 ms is in `web-20260930.txt` at 21:35:36). | Latest-wins draw loop: the hub hands a frame over and returns; frames that arrive meanwhile replace each other. Test: `WhileTheBrowserIsSlowToAcceptAFrame_…`. |
| The group membership is lost while the connection stays up (`UI-33`'s shared set is one known way), so no frame arrives until something re-subscribes. | A connected, hub-fed panel with no frame for **2 s** re-asserts its subscription and asks for a frame, then backs off (5, 10, 30 s, every 30 s). Tests: the four stall tests. |

### The instrument

Two log lines will say which side the next pause is on (radio-web; Warning and Information — both reach the
journal and the file sink; neither carries anything from the request):

- `Visualizer: no live frame for 2 s while connected; re-subscribing to {Mode} (UI-36)` and
  `Visualizer: live frames resumed after {Seconds} s (UI-36)` — the hub stopped delivering.
- `Visualizer: the browser took {Milliseconds} ms to accept one frame; frames were coalesced meanwhile (UI-36)`
  — the browser stopped accepting.

**If neither appears during a pause**, the panel's own stream was arriving (only frames for the mode on screen
count, since the hub connection is shared with every browser) and each frame was accepted within a second —
including a draw that ends in the interop timeout, which is timed in a `finally`. That points at the browser
not *presenting* them (a compositor/GPU stall after the panel's power-up), which nothing in this repo can fix
and which the CDP Long Animation Frame read above can be repeated to confirm. It is a pointer, not proof: a
pause shorter than the 2 s stall threshold, or draws each just under 1 s, would also log nothing.
⚠ One known false positive: straight after a radio-api restart, before any audio reaches the tap, the server
sends no frames by design and the panel logs one stall Warning.
