## Root cause — what it did, and why it errored

`DevTray.DumpAudioFrameAsync` (pre-fix `src/Radio.Web/Components/Shared/DevTray.razor:241-266`) did:

```csharp
await JS.InvokeVoidAsync("open", $"{apiBase}/api/audio/debug/dump-frame", "_blank");
```

That opens a **new browser window pointed at radio-api** (`ApiBaseUrl`, `http://localhost:5000` on the box).
The endpoint, `AudioDebugController.DumpAudioFrame` (`src/Radio.API/Controllers/AudioDebugController.cs:44-55`),
is **a deliberate `501 Not Implemented` stub** — the SoundFlow output stage keeps no re-readable buffer
of recent PCM, so there is nothing to dump yet (tracked there as "Arc follow-up #23"). Chrome renders the
501's JSON body as a page. On the kiosk there are no tabs, no address bar and no back button, so that
window is **a page a finger cannot leave**; the app is still running underneath it, unreachable.

The old comment said clicking it *"shows a 404 in the new tab — non-destructive"*. It was a 501, not a 404,
and on a touch-only kiosk it was the opposite of non-destructive. ⚠ **The API is not broken** — it says
exactly what it is. The defect was the Web side sending the browser to it. The API is unchanged.

## The fix

- **`SystemApiService.DumpAudioFrameAsync` / `DownloadLogsAsync`** fetch on the server side of the circuit
  and return an `ApiFileResult`: bytes and a file name, or a short display reason — the body's `error`
  field (this API's convention), else a problem-details `title`, else the status phrase, trailing full
  stop dropped, capped at 64 characters so it fits the card's three-line status. **No other body field is
  ever shown** (the logs 404 carries a server path). No response at all reads `radio-api unreachable`,
  `timed out waiting for radio-api` or `request to radio-api failed`.
- **`DevTray.RunFileActionAsync`** shows `dumping…` / `fetching…`, then the outcome, in the tapped card.
  Failures are red, successes green; the card is re-enabled either way, so a failure is recoverable by
  tapping again or closing the tray. Results clear on the next open. The auto-lock window restarts when
  a result lands so it stays readable.
- **`fileDownload.downloadFromStream`** (`wwwroot/js/fileDownload.js`) saves from a same-origin `blob:` URL
  through a temporary `<a download>` — a download, not a navigation. The blob is always
  `application/octet-stream`, so even if the `download` attribute were ignored the browser would treat it
  as a download rather than render a WAV or JSON viewer page.

## Evidence

- **bUnit** (`tests/Radio.Web.Tests/Components/Shared/DevTrayTests.cs`): 501 → reason in the card, card
  re-enabled; 200 → in-page save with the API's file name and size; logs requested with `period=1h`;
  API down → `radio-api unreachable`; logs 404 → only the `error` field, server path absent from the
  markup; browser refuses the file → said so; results cleared on reopen. The navigation tests assert
  **no `open` interop call, no `location` call, and the circuit's URI unchanged** — which is exactly
  what the old trap would trip. They cannot see what the browser does with the blob; the render below
  covers that.
- **Mutation-checked** (each mutation applied to the committed code, the suite run, the file restored;
  all killed by a failing test): injecting a `window.open` before the save, dropping the status code,
  reading the `path` field first, reporting a refused save as success, leaving the card disabled, not
  clearing on reopen, the wrong log period, not rendering the file name.
- **Local render at 1920×720** against a GET-only proxy in front of the box (POST/PUT/DELETE refused and
  never forwarded; `/hubs` 404; the logs download answered locally so the box zipped nothing; screenshots
  in the Builder's scratchpad, `ui2526-screens/`): the real box's 501 shows in the card; the logs card
  fired a real browser download (`radio-logs-1h-…zip`) with **one page open throughout and the URL
  unchanged**.

## Out of scope, recorded

- **The dump endpoint itself.** It stays a 501 until the output stage has a ring buffer to serialise
  (`AudioDebugController`'s summary describes what it needs). When it lands, the tray needs no change: a
  200 with a file is saved in-page already. That follow-up must also add the authorization gate the
  controller's summary asks for.
- **Where a kiosk download goes.** Chrome saves it to the box user's Downloads folder (or asks, if the
  profile is set to ask — a GTK dialog with a Cancel button). Nothing on the panel opens that folder;
  retrieving the file is an ssh job. The card says what was saved, not where.
