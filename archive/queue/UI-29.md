## What changed

- **Order:** Wave / Spectrum / Ring / Phase / **BAND** (was Wave / Spectrum / BAND / Ring / Phase, from
  `AUD-76`).
- **Availability:** the BAND tab is `disabled` (out of the tab order; the browser ignores taps on it),
  `aria-disabled="true"`, dimmed to `opacity: 0.35` with `cursor: not-allowed` — the same dimming as
  `.transport-btn:disabled` and `.phone-btn:disabled` — and its hover tint is suppressed. Its tooltip and an
  `aria-describedby` description say *"Available when the radio is the active source"*; the accessible name
  stays "Radio band map mode". `SelectMode` refuses BAND as well, for a tap that lands between the radio going
  away and the re-render.
- **"Radio active"** is the same signal BAND's tap-to-tune already used (`AUD-76`): `GET /api/radio/state`
  answers 400 when the radio is not the active source. The panel reads it at start-up and again on every
  `SourceChanged` (the server's broadcast, and MainLayout's local nudge after its own switch). A read that
  fails for any other reason (API down, 500) keeps the last answer, so BAND does not flicker away on a blip.
  Two more inputs keep it from going stale (review finding): a `RadioStateChanged` broadcast — which the API
  sends only while the radio is the active source — marks it active (recovering a failed start-up read), and
  BAND's own state read marks it inactive (recovering a missed `SourceChanged`).
- **Mode changes are serialised** (review finding). A tap, `SourceChanged` (often twice per switch),
  `RadioStateChanged` and BAND's own read can all change the mode, and each change awaits hub RPCs and JS. All
  of them now go through one `ReconcileModeAsync` under a gate, which shows `DisplayModeFor(preference, radio)`
  as it stands when the change runs and repeats until the screen matches. Start-up applies its mode under the
  same gate. ⚠ **No test discriminates the gate**: the races it closes open inside hub RPCs that the offline
  test transport completes synchronously, so removing the gate leaves the suite green (mutation `N6`). It is
  covered by reading, not by a test.

## The fallback rule (decided)

The saved preference (`ui.visualizer/defaultMode`) and the mode on screen are now two things
(`_preferredMode`, `_currentMode`), joined by `VisualizerPanel.DisplayModeFor`:

| Saved preference | Radio active | Shown |
|---|---|---|
| BAND | yes | BAND |
| BAND | no | **Spectrum** (the default) — the preference is **not** written |
| anything else | either | itself |

- Switching away from the radio while on BAND shows Spectrum and stops BAND's polling; switching back to the
  radio shows BAND again — automatically, because the preference still says BAND.
- **Any tap on an enabled tab is a pick and replaces the preference** — including tapping Spectrum while it
  is the fallback: that makes Spectrum the preference, and the radio returning then leaves Spectrum up.
- On page load, a saved BAND with the radio inactive opens on Spectrum, without a write.

Why not simply overwrite the preference with Spectrum on fallback: a source switch is not a choice about the
visualizer, and the owner would otherwise have to re-pick BAND after every trip to the file player.

## Effect on `AUD-76` / `AUD-91` / `UI-22` behaviour

Unchanged while BAND is shown: the map, per-band axis and markers, the colour tiers and legend, Scan, the
refresh cadence and the radio-state follow are untouched. Tap-to-tune's "switch to the radio first" path
(`TuneToAsync`, the 400 branch) is now reached only in the race where the radio goes away between the render
and the tap; it is kept as that guard, and its tests now model that race.

## The green dot (owner's question) — answer, no change in this row

It was **not** part of the Phase tab. It was the visualization hub's connection indicator,
`.visualizer-conn-dot` (`VisualizerPanel.razor:74-76` before this branch): `PR 4` collapsed the old
"Connected" pill into an 8 px dot pinned to the top-right of the picker header — green when the hub was
connected, red when not. The picker's last segment was Phase, so the dot sat on Phase's tab. The owner then
ruled it should go (*"there should be an indication in the visualization space - not a small dot"*); that is
**`UI-30`**, built in the same PR — the dot is removed.

## Deferred to the owner / Designer (polisher, MEDIUM)

**On the touch panel nothing visible says why BAND is grey.** The hint is a tooltip (never shown on touch)
and a screen-reader description; a tap on a disabled button does nothing. The owner's request — not
selectable unless the radio is active — is met, and there is no in-app pattern to copy for "explain a
disabled control on tap", so this is a design question, not a Builder fix. Also deliberately not taken: the
polisher's suggestion to keep the tab focusable (`aria-disabled` only, as `PresetBar`'s arrows do), because
the brief for this row said *not focusable*.

## Owner check

With the radio playing, BAND is the last tab and works as before. Switch to the file player: BAND greys out
and cannot be tapped, and if BAND was showing, Spectrum takes its place. Switch back to the radio: BAND is
tappable again and, if it was showing before, it comes back by itself.
