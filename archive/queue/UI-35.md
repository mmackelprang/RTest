## Why it got slower

The server switch is as fast as it was (0.03–0.7 s, measured). The Web side waited on the queue:

- `MainLayout.HandleSourceChangeAsync` awaited the switch POST, set `_selectedSourceId` **without rendering**,
  then awaited `HubService.NotifySourceChangedAsync()`. `AudioStateHubService.NotifyAsync` awaits its
  subscribers one after another (`UI-7`), so the pill lit only when every subscriber had finished.
- One of them, `QueueHistoryPanel.SyncSourceAsync`, read `GET /api/sources/primary`, then awaited
  `RefreshQueueAsync` → `GET /api/queue/full` (**1.4–4.7 s on the box**, see [`AUD-96`](AUD-96.md)), and only
  then set the tab. It did so **when switching to Radio, Bluetooth or Vinyl too**, because
  `QueueController.TryGetQueueSource` falls back to the cached File Player.
- `SourceChanged` fires **twice** per switch (MainLayout's local notify, then the hub broadcast), so the queue was
  read twice.
- Before `UI-17` (#715, `52bf2ea6`), `Home.razor` toggled the panel around the POST and the queue panel was not
  mounted on Radio — which is why it used to feel snappier.

## What changed

- **`QueueHistoryPanel.SyncSourceAsync`** decides the tab from the source read alone on a switch, and its caller
  renders at once. The queue is re-read **in the background**, and only for a change **to or from File Player**.
  When that read lands, File Player's default tab (Queue when it has tracks, else History) is re-applied with the
  fresh count — unless the owner has tapped a view meanwhile. A **repeated `SourceChanged` for the same type**
  does nothing beyond the source read — except the read that recovers from a failed one, which re-reads the queue
  once, since a queue change made during the outage may have been missed. **The mount is unchanged**: the first read still loads the queue before
  choosing a tab, since nothing waits on it.
- **`MainLayout`** calls `StateHasChanged()` right after the switch POST succeeds and before notifying, so the
  pill lights without waiting for the subscribers.
- `UI-17`'s per-source defaults, the tapped-view override and the Bluetooth auto-switch are unchanged, as are
  `UI-29` / `UI-30`. The only edits to `QueueHistoryPanel.razor` are in `SyncSourceAsync`, one new method
  (`RefreshQueueForSourceAsync`), a `_disposed` flag and its one line in `DisposeAsync` — the action row, menu and
  dialogs (being changed by `UI-32` / `UI-34`) are untouched.

## Tests

`QueueHistoryPanelSourceSwitchTests` (8) — the queue read is **held open** with `RoutedApiHandler.Hold`, so
"before the read completes" is a fact rather than a timing: File Player → Radio shows the Radio tab while the read
is held and the `SourceChanged` dispatch has already returned (the owner's case); Vinyl → File Player shows Queue
while held; a repeated `SourceChanged` reads the source but not the queue; Radio ↔ Vinyl never reads the queue;
File Player's default is re-applied when the fresh count lands; a view tapped before it lands is kept; a read
landing after a switch away leaves the new tab alone; recovering from a failed source read re-reads the queue once.
`MainLayoutSourceSwitchTests` (1): with the switch POST held until released (so it completes asynchronously, as
against the real API) and a `SourceChanged` subscriber held on a gate, the pill is unlit before the POST succeeds,
lit while the subscriber is still held, and the layout's handler has not returned.

## Owner checks (after deploy)

1. Switch between sources (File Player, Radio, Bluetooth, Vinyl): the **centre panel and the source pill change
   within about a second** of the tap.
2. Switching to File Player opens on the Queue tab when the queue has tracks (History when empty), as before.
3. Tap a tab, then switch away and back: the new source opens on its own default.
