# `UI-15` — `isFirstRun` conflates "never seen a source" with "currently no source", so a real source change is silently not broadcast

[← Builder Queue index](../../docs/BUILDER_QUEUE.md)

🟡 **P2.** Filed 2026-09-09 by the `UI-13` Builder, from its pre-merge review (finding `L5`). ⛔ **Not
caused by `UI-13` and not worsened by it** — the defect is identical in both orderings, which is why
it was filed rather than folded in.

## The defect

`src/Radio.API/Services/AudioStateUpdateService.cs`, `CheckSourceChangedAsync`:

```csharp
var currentSourceType = activeSource?.Type.ToString();   // null when there is no active source

if (currentSourceType != _lastActiveSourceType)
{
  // Skip broadcast on first poll (null → initial value) to avoid spurious SourceChanged
  var isFirstRun = _lastActiveSourceType == null;        // ⚠ ALSO true whenever the last observed
                                                         //    state was "no source"
  if (!isFirstRun)
  {
    await _hubContext.Clients.All.SendAsync("SourceChanged", cancellationToken);
    _logger.LogInformation("Broadcast SourceChanged: {SourceType}", currentSourceType ?? "None");
  }

  _lastActiveSourceType = currentSourceType;
}
```

`null` is doing two jobs. It is the sentinel for *"this service has not yet observed anything"*, **and**
it is a legitimate observed value — `IAudioSourceManager.ActiveSource` is declared `IAudioSource?`
(`IAudioSourceManager.cs:13`) and `activeSource?.Type` handles null deliberately.

⭐ **So every `null → non-null` transition is treated as a first run and suppressed.**

## The reachable case, stated as narrowly as it can be proven

**If `radio-api` starts with no active source, the user's first source selection is never
broadcast.** Trace:

| Tick | `ActiveSource` | `currentSourceType` | Outer `if` | `isFirstRun` | Broadcast? | Cache after |
|---|---|---|---|---|---|---|
| 1..n | none | `null` | `null != null` → **false** | — | no | `null` |
| n+1 | user picks Radio | `"Radio"` | true | **true** | ⛔ **NO** | `"Radio"` |
| n+2 | user picks Bluetooth | `"Bluetooth"` | true | false | yes | `"Bluetooth"` |

The *second* source change broadcasts; the first does not. The same suppression recurs on any later
`source → none → source` sequence.

⚠ **What is NOT established, and must not be assumed:** whether `AudioManager._activeSource` is ever
reset to `null` after startup. It is assigned in exactly one place (`AudioManager.cs:235`,
`_activeSource = source;`) and the Builder did not trace whether that argument can be null. **So the
`source → none → source` recurrence is plausible but unproven; the startup case above needs only that
the box can idle with no source, which is the default state before any selection.**

## Why it matters

`SourceChanged` is the event the console surface uses to re-sync when the active source changes. A
suppressed one leaves the panel showing the previous source — the same
`AUD-12` / `GV-12` / `UI-13` family: **state that stops tracking reality with nothing reporting a
fault.** Nothing logs, because the `LogInformation` sits inside the same suppressed branch.

## Scope questions for the plan

1. **What is the right sentinel?** The obvious fix is a separate `bool _hasObservedSource` (or a
   sentinel string) so `null` can be an ordinary value. ⚠ Do not "fix" it by broadcasting on the true
   first run — the suppression exists on purpose, to stop a spurious `SourceChanged` at startup.
2. ⚠ **Establish reachability on the box BEFORE writing code.** Does `radio-api` restore a source at
   startup? If it always has one by the first poll, the startup case never fires and this row may be
   much smaller than it looks — or may close as "unreachable, documented". ⛔ **This repo's stated
   pathology is rows filed on premises nobody checked; check this one.**
3. **Can `ActiveSource` return to `null`?** Answers whether the recurrence exists at all.
4. **Is it user-visible?** The UI may already re-sync via the REST response to the user's own source
   switch, in which case the missing broadcast affects only *other* connected clients. **Verify before
   claiming user impact** — the Builder did not.

## Verification

Unit-testable with no new production seam, exactly as `UI-13` did it: drive `CheckSourceChangedAsync`
directly by reflection with `null → "Radio" → "Bluetooth"` and assert the **first** transition
broadcasts once the fix lands. ⚠ **Must be RED first.** Today it is silently suppressed, so a test
written against `main` asserting a broadcast on `null → "Radio"` fails by construction — confirm that
rather than assuming it.

⭐ `tests/Radio.API.Tests/Services/AudioStateUpdateServiceCacheOrderingTests.cs` already carries the
harness (`CreateService`, `InvokeCheck`, `BareSource`) and one test that pins the *current* behaviour —
`TheFirstSourcePollEstablishesTheBaselineWithoutBroadcasting`. ⚠ **That test must keep passing**: it
covers the genuine first run, which this row does not change.

Likely auto-mergeable — no hardware, no live-audio path, unit-testable. Confirm in the plan.

## Shipped — 2026-09-29 (branch `fix/aud-5-80-ui-15-cast-volume`, with `AUD-5` and `AUD-80`)

### Reachability, established on the box first (file sink, read-only, 2026-09-23 … 09-29)

- **Every logged startup restores a source before the first poll: 33 of 33.** Per day, the count of
  `AudioStateUpdateService starting` equals the count of `Switching from source none to …`
  (09-25: 4/4, 09-26: 2/2, 09-27: 1/1, 09-28: 17/17, 09-29: 9/9), and the restore always precedes the
  service start by 1–4 s (e.g. 16:49:45.773 restore → 16:49:49.173 service start). So the startup
  case has **not occurred on this box** in the retained logs.
- **`ActiveSource` cannot return to `null`.** `AudioManager._activeSource` is assigned only in
  `SwitchSourceAsync` (`AudioManager.cs:274`), which throws `ArgumentNullException` on a null source
  first. So the `source → none → source` recurrence the row calls "plausible but unproven" is
  **unreachable**.
- Remaining reachable path: a startup whose source restore does not happen or fails (e.g. the
  restore path throws). Not observed, but nothing in the code rules it out.

**Decision:** fixed anyway — it is a real defect in the code, the fix is a field and an early return,
and it does not change the genuine-first-run behaviour.

### What landed

`AudioStateUpdateService.CheckSourceChangedAsync` takes its baseline on the first poll behind a
separate `_hasObservedSource` flag, so `null` ("no source") is an ordinary observed value.
`TheFirstSourcePollEstablishesTheBaselineWithoutBroadcasting` still passes; new test
`TheFirstSourceSelectedAfterStartingWithNone_IsBroadcast` drives none → none → Radio → Bluetooth and
asserts the Radio selection broadcasts.

**User impact (row question 4), not verified in a browser:** given the reachability above, none on this
box today. No hardware, no live-audio path; unit-tested only.
