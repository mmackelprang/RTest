## The request (owner, 2026-10-02, verbatim)

> *"For file player, the three-dot menu isn't super touch friendly. Can we move these options to a more visible place? On top of 'Add Files', 'Load Playlist' and 'Clear All' we should also have 'Add Folder' with an option to include subfolders."*

## What was there

`UI-17` put a ⋮ (32 × 32 px, 18 px glyph) at the right of the File Player Queue tab strip. It opened a menu of three 44 px rows in 13 px text — Add Files, Load Playlist, Clear All — and Clear All emptied the queue on one tap, with no confirmation. Save as playlist was already on screen, as a tile under the Queue Total. Screens: `00-before-home.png`, `01-before-kebab-open.png` (scratchpad `ui32-screens/`).

## What changed

**The menu is gone; its actions are on screen** (designer consult, session model, 2026-10-02). The Queue view's right column (220 px) holds the Queue Total tile and, under it, one stack of full-width 56 px (`--touch-preferred`) buttons, icon leading, in the old Save tile's mono-uppercase outline treatment:

| Button | Emphasis | Shown | Disabled |
|---|---|---|---|
| Add files | accent outline | File Player only | never |
| Add folder | accent outline | File Player only | never |
| Load playlist | accent outline | File Player only | never |
| Save as playlist | neutral outline | every queue view | queue empty |
| Clear queue | red outline, at the bottom behind a rule | File Player only | queue empty |

Add/Load/Clear stay File Player only for the reason `UI-17` gave: adding makes the API switch the source to File Player, so the queue view reached from another source by the Queue pill must not offer them. Measured at 1920×720: column 220 × 549, buttons 208 × 56, nothing wraps or overflows.

**Clear queue asks first** — a 56 px button is easier to hit by accident than a menu row. "Clear the queue?" / "Removes all N tracks and stops playback." (`FilePlayerAudioSource.ClearQueueAsync` calls `StopAsync`, so "stops playback" is what the code does.) Cancel first; tapping outside cancels.

**Empty queue** reads "Queue is empty" / "Add files, a folder, or a playlist to start.", pointing at the buttons beside it.

**Add folder** opens the file browser in a new folder mode (`FileBrowserDialog.SelectFolder`):
- only folders are listed (a file row would look tappable and do nothing), and the file-type filter is hidden (Add folder queues every supported type);
- a summary line says what adding the shown folder would queue — counted on each navigation **without** opening every file (`checkReadable=false`; one NAS open a file is too much to spend per tap): *"0 tracks here · 60 including subfolders"*, *"No tracks directly in ABBA. Turn on Include subfolders to add 60."*, *"More than 500 tracks here. Only the first 500 will be added."*, *"No playable tracks in …"*;
- **Include subfolders** is a switch, **on by default** — measured on the box, artist folders hold no tracks at the top level (below), so off would add nothing in the common case;
- the button names the folder and the count — `Add "ABBA" (60)`, `Add this folder (N)` at the library root or a bookmark, `Add first 500` over the cap — and is disabled while counting or when there is nothing to add;
- Add lists the folder again — with the switch's subfolder setting and **with** the readability check — shows *"Checking tracks…"*, then queues the tracks in batches with a progress bar and *"Adding 20 of 60…"*, then closes with a toast: *"Added 60 tracks from ABBA"*, *"… · 4 skipped (unsupported or unreadable)"*, or the error.

|---|---|---|---|

| `Aerosmith` | 0 | 33 | 3 |
| `3 Doors Down` | 0 | 68 | 4 |

| `10cc` | 0 | 18 | 2 |
| `/mnt/nas_media/Music` (the library) | — | **12,649** | 1,158 (349 artists) |

A cold walk of the whole library took **15.0 s**; there were **0** symlinks in it. Reading the first 256 KB of each of `3 Doors Down`'s 68 files cold took **12.5 s** (~184 ms a file) — the order of what the API spends reading tags as it queues each one.

## Server side — `GET /api/files/folder-tracks?path=&includeSubfolders=`

Lists; queues nothing. The Web queues the returned paths through the existing `POST /api/files/queue`, 20 per request (`FolderQueueAdder`): at ~180 ms a file a 500-track folder in one request would outlive the Web's 30 s `HttpClient` timeout with no way to tell how far it got.

- **Order:** depth-first — the folder's own files by natural name order (`NaturalStringComparer`: "2 - …" before "10 - …", "Disc 2" before "Disc 10"), then each subfolder whole, in natural order. An artist folder queues album by album, track by track.
- **Guard, two checks.** (1) The existing lexical one: an absolute path must pass `FilesController.IsPathAllowed` (the check `POST /api/files/queue` applies to each path later), and every path goes through `FileBrowser.GetFullPath` (`..` normalised away; the result must be the media root, an allowed browse directory or a bookmark, with a trailing-separator prefix match). (2) **New:** the folder's *real* path — every symlink along it resolved, component by component (`FileBrowser.ResolveRealPath`) — must sit inside the real path of one of those directories. `Path.GetFullPath` resolves no links, so without (2) a link inside an allowed tree pointing at `/etc` passes (1). A media root configured through a link still works: the allowed directories are compared by their real paths too.
- **The walk never follows a link** — linked files and folders are skipped and counted — so nothing below the checked folder can lead out of it, and a link cycle cannot loop it. Hidden and system entries are ignored (on a NAS that includes the `._Song.mp3` AppleDouble files a Mac leaves). A supported file that cannot be opened for reading is skipped and counted; a subfolder that cannot be listed is skipped and counted; the chosen folder itself failing to list is a 500.
- **Cap:** `FilePlayer:MaxFolderTracks` (500). The walk stops at the first track past it and returns the first 500 in queue order with `truncated: true`; nothing past that point is read. 500 admits any artist or album measured above and stops a tap on the library root from queueing 12,649 tracks.
- **Not on the request thread:** the walk is synchronous filesystem I/O on a NAS, so it runs on the thread pool. The request stops waiting for it (`Task.WaitAsync`) after `FilePlayer:FolderScanTimeoutSeconds` (20 s → 504 with a message) or when the client disconnects — **even if the walk is stuck inside one blocking call** (a stale CIFS mount, a FIFO named `*.mp3`); the walk itself checks the token between entries and stops at its next check, holding its thread-pool thread until then.
- **`checkReadable`** (default true): `false` skips the per-file open, for a caller that only wants the count.
- **Errors:** 400 outside the allowed directories or a malformed path (e.g. an embedded NUL), 404 missing, 504 timeout, 500 unreadable. Bodies carry a fixed message only — no path, no exception text.
- The real-path comparison is **case-sensitive except on Windows** (on Linux `/mnt/NAS_MEDIA` is not `/mnt/nas_media`); the older lexical checks ignore case everywhere, and this one runs after them. `..` after a link is applied against the link's target, as the kernel does.

The `IsPathAllowed` XML comment claimed `GetFullPath` eliminates symlinks; it does not, and the comment now says so.

- `NaturalStringComparerTests` (Core).
- `FolderQueueAdderTests`, `FileBrowserDialogFolderModeTests`, `QueueHistoryPanelTests` (Web, bUnit against a canned API): the action stack and its order, ⋮ gone, File-Player-only actions, disabled states, the Clear confirmation (cancel, tap outside, confirm → `DELETE /api/queue`), folder mode (folders only, the summary, the button text at root / in a folder / over the cap, the switch, batches of 20 in order, the close result, the switch not inside a `<label>`).

**Mutation-checked — 33 mutations: 32 killed by a test failure, 1 deliberate survivor.** Each was applied to committed code, the named suite run, and the file restored with `git checkout --` (round 2 in a detached worktree outside the repository). Six first-round mutations were initially "killed" by compile errors (warnings are errors in Release: unreachable code, constant filters) and were rewritten as runtime-equivalent forms before counting.
- *Server:* link-resolving check off; links followed; ordinal file sort; cap off by one; always recurse; hidden not skipped; unreadable not skipped; subfolders pushed in the wrong order; timeout not mapped to 504; disconnect reported as a timeout; natural digit compare off; both guards off; top-level miscount; `WaitAsync` removed (a blocked walk holds the request); `checkReadable` ignored; `..` after a link a no-op; NUL path → 500.
- *Web:* Clear without confirmation; the confirmation outliving the queue view; Esc ignored; Add actions on every source; the disposed token source kept (the review HIGH); batches reordered; no stop on a failed batch; the count listing opening every file; the cap ignoring a full top level; the switch inside a `<label>`; the type filter in folder mode; caller cancellation reported as a failure; file rows in folder mode; the switch defaulting off; UI-34's `min-width` restored.
- ⚠ **The survivor, by design:** skipping only the *lexical* guard leaves every traversal test green, because the link-resolving check rejects the same paths on its own — two independent sufficient checks, not one check in two halves. With both off, the guard tests fail.

`OnLinux_TheRealPathCheck_IsCaseSensitive` is a `SkippableFact` that skips on Windows; on this Windows dev host it skipped, so it has only run where CI runs it. The symlink tests ran on Windows (the host can create links) and skip, rather than fail, where links cannot be created.

## Pre-merge review and polish (session model)

**Review — 1 HIGH, 2 MEDIUM, 6 LOW; the endpoint's traversal and symlink defence held.**
- **HIGH, fixed:** an unlistable folder (e.g. an unmounted bookmark) left the dialog's listing token source disposed but still referenced; the next navigation's `Cancel()` threw `ObjectDisposedException`, which on Blazor Server ends the circuit — the kiosk UI would die. The field is now detached before cancelling. Test: success → unlistable → navigate (mutation W5 kills it).
- **MEDIUM, fixed:** the 504 claim was false for blocking I/O — cancellation was only checked between entries. Now `WaitAsync`; comments say what happens to the walk itself.
- **MEDIUM, fixed:** every folder-mode navigation opened up to 500 files on the NAS. The count now skips the open; Add re-lists with it.
- **LOW, fixed:** `..` after a link resolved lexically; case-insensitive real-path compare on Linux; NUL path → 500; the API client reported caller cancellation as a failure (and logged it); the cap message missed a top level that alone reached the cap; the Clear confirmation could outlive the queue view. Comment wording on the cap ("nothing past that point is read") and on the 180 ms/file figure (it is a raw-read measurement) corrected.
- **LOW, deferred:** *check-then-walk race* — the walk enumerates the checked path, not its resolved real path, so an ancestor swapped for a link between the check and the walk would escape. Walking the real path would close it but would hand `POST /api/files/queue` real paths its lexical guard rejects when the media root is configured through a link. Needs local write access to the media tree; recorded, not fixed. *Bind mounts* are not reparse points and would be walked; same precondition.

**Polish — 0 HIGH, 4 MEDIUM, 6 LOW.** Fixed: the file-type filter hidden in folder mode (which then exposed a layout bug — see below); Cancel buttons in the app's text style; the Clear confirmation focuses Cancel and Esc cancels; the empty-queue hint in `--text-medium` (was ~2.2:1); Save as playlist's outline visible (`--text-low`); label tracking back to 0.08em (measured: no label overflows).
