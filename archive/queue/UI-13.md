# `UI-13` — a failed broadcast still advances the change-detection cache, so the delta is never re-sent

[← Builder Queue index](../BUILDER_QUEUE.md)

🟡 **P2.** Filed 2026-09-09 by the `UI-12` Planner, found while enumerating senders and flagged as out
of that row's scope rather than folded in.

## The defect

`Radio.API/Services/AudioStateUpdateService.cs:477` assigns `_lastRadioState` **before** the
`await SendAsync` that broadcasts it:

```csharp
_lastRadioState = dto;          // :477 — cache advanced
await SendAsync(...);           // may throw, may be cancelled
```

The cache is what change-detection compares against. So **if the send throws or is cancelled, the
cache has already moved on, and that delta is never re-broadcast** — the next comparison sees "no
change" against a state the clients never received.

⭐ **The failure is silent and self-erasing:** there is no retry, and the evidence that a broadcast was
missed is destroyed by the same statement that misses it.

## It is a shape, not a single line

The Planner found the identical ordering at **`:266`, `:279`, `:453-454`, `:502`** as well as `:477`.
⚠ **Fix the shape, not the instance** — a plan that repairs one and leaves four is worse than none,
because it makes the class look handled.

## Why this matters more than it looks

The clients affected are the ones that drive the whole console surface — radio state, now-playing,
volume. A missed delta does not show as an error; it shows as **a panel that is quietly out of date
until something unrelated changes and forces the next broadcast.**

That is the same family as `AUD-12` (a source stuck at `Ready` while audio plays) and `GV-12` (a panel
stuck on an error after the backend recovers): **state that stops tracking reality with nothing
reporting a fault.**

## Scope questions for the plan

1. **Is assign-after-await always correct here?** Moving the assignment after the `await` fixes the
   missed delta, but ⚠ **check for re-entrancy first** — if two updates can interleave, a late
   assignment can write a stale value over a newer one. Establish whether this service is serialised
   (a timer? a single hosted loop?) before assuming the swap is safe.
2. **What should happen on a genuine send failure?** Not advancing the cache means the next tick
   re-sends — which is probably right, but it also means a persistently failing client causes repeated
   full broadcasts. Say which is intended.
3. **Does `SendAsync` actually throw, or swallow?** If it already catches internally, the cache-advance
   may be unreachable and this row is a tidy rather than a fix. ⚠ **Establish that before writing a
   test that cannot fail.**
4. **Are all five sites the same shape?** They were found by pattern. Read each — one may be
   deliberately ordered that way for a reason the others are not.

## Verification

Unit-testable: make the send throw, then assert the **next** cycle re-broadcasts the same delta.
⚠ **Must fail first** — today the second cycle sees "no change" and sends nothing, so the test is RED
against `main` by construction. **Confirm that rather than assuming it.**

⚠ `CLAUDE.md` § *Test Timing*: this service is timer-driven. **Do not race a wall clock** — use the
injectable `TimeProvider` idiom (`EncoderHudService` is the worked example) and synchronise on the
observation, not on elapsed time.

Likely auto-mergeable — no hardware, no live-audio path, unit-testable. Confirm in the plan.

### `SendAsync` cannot throw on a failed broadcast

Established twice independently — by reading the ASP.NET Core source, and by running a **real Kestrel
host with real WebSocket clients** on `Microsoft.AspNetCore.App` 10.0.11. The governing line,
`HubConnectionContext.cs:361` (`release/10.0`):

```csharp
catch (Exception ex) when (ex is not OperationCanceledException || !cancellationToken.IsCancellationRequested)
```

Everything else is caught at `:341-349`, logged, the **connection** aborted, and a **successful**
`FlushResult` handed back. Measured:

| Scenario | Result |
|---|---|
| Hard-killed socket | **129 consecutive sends over 8 s, zero faults** |
| Graceful client stop | nothing faulted |
| Unserializable payload | client dropped, **caller saw success in 8 ms** |
| Nonexistent / emptied group | 0 ms no-op |

With no matching connection, `DefaultHubLifetimeManager.cs:136-139` returns `Task.CompletedTask`
**without inspecting the token at all.**

### Cancellation does escape — and it is the one exception that means "stop"

The production shape was reproduced verbatim: cache advanced, `TaskCanceledException` thrown, client
received zero messages, connection still healthy. **But both escape conditions need the caller's token
cancelled, and that token is always `ExecuteAsync`'s `stoppingToken` (`:191`).** Four lines below the
loop (`:196-199`):

```csharp
catch (OperationCanceledException) when (stoppingToken.IsCancellationRequested)
{
  // Normal shutdown, don't log as error
  break;
}
```

⭐ **The only exception `SendAsync` can produce is the one `ExecuteAsync` treats as *stop and exit*.**
`Program.cs:134` registers the service `AddHostedService` only, so there is no second instance to read
the stranded cache. **It dies with the process.**

### ⚠ Why the row is KEPT rather than closed — and what its deliverable actually is

**Not the bug fix. The written-down precondition.** The current safety rests entirely on *"the only
canceller is shutdown"* — **a backplane, or any call site passing a different token, makes this defect
live AND silent.** That is a plausible future for this repo, and the failure would arrive with no
error and no recovery.

⛔ **Do not build this ahead of a row with a live user-visible defect.** ⚠ **Closing it with this
correction appended is also defensible** — the plan's §0.9 argues both, and the Planner explicitly
would not argue hard against closing. **Owner's call.**

### ⛔ Four more premises fell — the sharpest was found by the pre-merge reviewer

1. ⭐ **The regression guard covered ONE site of six, and the plan's `M3` was too weak to notice.**
   **Measured:** with only the volume guard present, replacing `_lastPlaybackState`'s assignment with
   `null` left **all 8 tests GREEN** — while re-broadcasting an unchanged state twice a second
   forever, a client storm on a box where `CLAUDE.md` records CPU churn as audible. The same held for
   `_lastNowPlaying`, `_lastQueueSnapshot` and `_lastRadioState`. **Four per-site guards added**, each
   verified to fail on exactly its own mutation. ⚠ In all four cases the site's *cancellation* test

   cache, because they only invoke twice.
2. ⛔ **The precondition comment invalidated its own line reference in the commit that wrote it.** It
   cited `:196` for `ExecuteAsync`'s shutdown catch; the comment's own 27-line insertion had moved

   the argument for naming.
3. ⛔ **"Records *the clients have this* as a fact before it is one" was refuted by the evidence
   eleven lines below it.** A completed `SendAsync` is **not** proof of delivery — the same comment
   documents 129 sends to a hard-killed socket all returning success while the client received
   nothing. The conclusion (assign after) is right; the *reason* overclaimed. The comment now says
   what the cache can actually hold: the last state whose broadcast returned without faulting.
4. ⛔ **"The eight `async void` handlers" is nine.** `:803, :817, :832, :883, :897, :994, :1017,

### ⚠ A trade the plan did not state, now written down

On a **persistent** fault the new ordering retries every ~500 ms, logs at `ExecuteAsync`'s catch-all
every tick, and **starves every check ordered behind the failing one** — `CheckSourceChangedAsync`
runs first, so a permanent fault there means the other five never run again. On `main` the service
instead went silent after one pass and never recovered. The reorder is still right — it is strictly
better on a transient fault and is the only version that recovers at all — but "already handled" was
an overclaim and has been corrected in the test remarks. ⛔ **No backoff row was filed:** the fault is
unreachable today, and filing a row on an unreachable premise is this repo's stated pathology.
