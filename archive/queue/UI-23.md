# `UI-23` — drag the preset bar with a finger

[← Builder Queue index](../../docs/BUILDER_QUEUE.md)

✅ **CLOSED 2026-10-01 — no code change. Finger-drag already works with what `UI-20` shipped.**

## The request

Owner, `UI-20` panel UAT 2026-10-01, check 2 (*"◀ ▶ paging, hold-to-repeat and swipe"*):

> *"2- passes, but I'd like to be able to "drag" the bar in addition to pressing the arrow keys."*

Filed the same day as a request to drag the strip with a finger: the strip would follow the finger 1:1 and
snap to a card edge on release.

## Why it closed with no code

The owner re-tested on the box, which was then running `f77049b` (the `UI-21` build, with no `UI-23` code):

> *"Drag presets works."*

`UI-20`'s strip is a native horizontal scroller (`overflow-x: auto`, `scroll-snap-type: x mandatory`,
`touch-action: pan-x` in `design-system.css` §"Preset bar"), so a touch drag pans it natively and snaps on
release. The coordinator dropped the build, because a second, scripted drag path would only add
gesture-conflict risk next to tap-to-recall, long-press, the arrows and the knob mirror.

## What the investigation measured before the scope change

The strip was driven in real Chromium (Playwright, trusted input through CDP
`Input.dispatchTouchEvent` and the mouse) against the shipped `preset-bar.js` and CSS. This was a harness,
not the kiosk.

| Gesture | Strip moved? | Card handlers saw |
|---|---|---|
| Touch drag, 20 steps | **yes** (0 → 279 px), one `OnManualScroll` | `pointerdown`, then `pointercancel` (no `pointerup`, no click) |
| Touch: hold 800 ms, then drag | **yes** (0 → 270 px, on a card edge) | `pointerdown`, then `pointercancel` |
| Mouse drag (with or without a hold) | **no** (stays 0) | `pointerdown`, the module's synthetic `pointercancel`, no click |
| Touch tap / touch long-press | no, as intended | `pointerdown`, `pointerup`, click |

**Nothing in the code swallows a touch drag.** The long-press and tap paths never call `preventDefault`.
The module's >10 px synthetic `pointercancel` is dispatched to the card only, and cannot cancel a native
pan. The only input that cannot drag the strip is a **mouse-type pointer**.

⚠ **Why the first attempt seemed not to work is not established.** The box was off-limits during the
owner's test, so how the kiosk delivers the ILITEK touchscreen's input (touch or emulated mouse) was not
probed. The harness rules out a code path that eats touch drags. It does not rule out a one-off on the
panel, such as the press landing on an arrow, or a gesture read as a tap. If drag ever fails again, the
first probe is a read-only CDP query on `:9223` for the `pointerType` of a drag on the strip. If the answer
is `mouse`, the strip needs a scripted drag path; if it is `touch`, the native pan is being cancelled by
something else.
